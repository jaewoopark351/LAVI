## 5. 후속 작업: 시나리오 A 한 번

### 5.1 현재 증거부터 확인

1. 현재 Git 상태와 실제 소스를 대조하고, 자동 발동 임계치·정리 목표·보호/제외 정책을 읽는다. 예시인 34/36 또는 36/36을 고정 계약으로 대신 쓰지 않는다.
2. `confirmedStoredItems` 증가 지점을 호출 경로와 함께 따라간다. 이 단계에서는 카운터의 의미·성공 판정을 변경하지 않는다.
3. 실제 게임의 원본 로그 경로와 출력 설정을 찾는다. 런처 이력, LAVI 초기화·모델 로딩 로그를 보관 실행 로그로 대신하지 않는다.
4. 재시작이 필요하다면 먼저 기존 원본 로그를 저장소 안의 새 수집 폴더에 보존한다. 원본 경로·수집 시각·시간대·PID·세션·회전/잘림/억제 여부를 기록하고, 원본과 행 번호를 포함한 분석용 발췌를 분리한다. 외부 전달본에서는 비밀값을 제거한다.
5. 빌드 입력·JAR 식별 정보를 실제 배포 JAR와 연결한다. 이미 확보한 유효한 빌드 근거는 재사용하되, 소스가 바뀌거나 산출물 관계가 불명확하면 그 부분을 다시 확인한다. 디스크 JAR 교체와 실행 프로세스의 새 클래스 로딩을 구분한다.

실제 게임 조작이 사용자에게 필요하면 자동화할 수 없는 이유와 필요한 최소 준비·조작을 구체적으로 안내한다. 그동안 가능한 소스 조사·로그 수집·분석은 계속한다. 기존 월드·미저장 작업을 보호하고 관계없는 프로세스를 종료하지 않는다.

- 접근 가능하고 공간이 있는 가까운 상자와 보관 가능한 surplus를 준비한다. 대상 차원·좌표와 시작 상태를 기록한다.


자동 작업에는 명령 requestId가 없을 수 있다. 실제 존재하는 operation/maintenance/child/store 식별자를 따라 연결하고, 없는 필드는 만들지 않는다. 필요한 인벤토리·상자 수량 전후 대조와 서버 동기화 후 유지 관측을 확보한다. GUI를 다시 열어 확인하는 경우 그 조작의 시점도 구분한다.

## 6. 관측 보완과 기능 변경의 경계

먼저 올바른 로그 수집, 기존 로그 설정, 게임 상태 전후 대조로 확보 가능한지 확인한다. 그래도 A 판정에 필요한 핵심 관측이 부족할 때만 기존 진단 경로의 최소 보완 범위를 정한다. 새로운 scheduler, 전역 manager, 별도 검증 프레임워크, 매 tick 대량 덤프를 만들지 않는다.

패치 보고서와 대조할 탐색 키워드는 `AUTO_DEPOSIT_EXECUTION_PROGRESS`, `AUTO_DEPOSIT_BUDGET_LIMIT`, `AUTO_DEPOSIT_ROOT_SETTLED`, `AUTO_DEPOSIT_RUN_FINAL`이다. 현재 소스의 실제 대응 이벤트·필드를 확인해야 하며, 이 목록은 이번 게임 실행에서의 출력 확인을 뜻하지 않는다.

- 확정 종료 사유, callback 사유, 실제 제한 종류, 현재 phase, 마지막 인정 진척과 예산을 구분한다. client tick과 budget execution tick을 혼용하지 않는다.
- 로그 억제는 동작 부재의 증거가 아니다. 출력 실패가 동작 제어·성공 판정을 바꾸면 안 된다.
- 관측 코드를 추가했다면 필요한 테스트·재빌드를 수행하고, 수정 전 실행 결과를 수정 후 코드의 증거로 사용하지 않는다.
- 실제 기능 오류가 확인되면 증거와 필요한 수정 범위를 먼저 제시한다. STOP·자동방어·보호 아이템·working-set·KEEP_LOADOUT·정확한 GUI 바인딩·실행 제한·동일 실패 반복 방지를 약화하지 않는다.

## 7. 시나리오 D와 전체 회귀는 별도

정상 보관 후 인벤토리가 다시 찼을 때 재실행되는 조건은 현재 소스와 계약에서 확인한다. 현재 보장 동작과 원하는 동작이 다르면 별도 항목으로 기록한다. D의 정책 변경을 A의 선행 조건으로 삼거나 관측 보완에 섞지 않는다.

A가 통과해도 장시간 준비·접근(B), 실제 무진척·반복(C), 재발동(D), 방어·STOP(E), 실제 Chat·마이크(F)까지 통과한 것이 아니다. 특히 합성 2,400틱 검사를 실제 게임의 장시간 재현으로 보고하지 않는다. 무진척 시 기대한 제한 종료가 관측된다면 해당 방지 테스트의 PASS가 될 수 있다.

## 8. 다음 보고의 최소 형식

결과는 아래 세 부분으로 정리한다.

1. **현재 소스와 실행 근거로 확인한 사실** — 무엇을 실행했고 어느 파일·행으로 확인했는가.
2. **아직 확인하지 못한 사실과 이유** — 미실행, 관측 누락, 출력 억제, 환경 제약을 구분한다.
3. **다음 검증에 필요한 최소 작업** — 사용자에게 필요한 조작이 있으면 그 부분만 명시한다.

| 검사 ID/판정 대상 | 기대 결과 | 실제 결과 | 판정 | 실행·작업 식별자 | 근거 파일·행 또는 미확인 이유 |
| --- | --- | --- | --- | --- | --- |
| A / 전송·압력·종료를 각각 기록 | 현재 소스 계약에 맞춰 작성 | 실제 관측값 | PASS / FAIL / NOT_RUN / BLOCKED | 실제 존재하는 값 | 원본 근거 또는 부족한 관측 |

PASS는 해당 기대 결과를 근거로 확인한 경우, FAIL은 실행 결과가 기대와 다른 경우다. NOT_RUN은 미실행, BLOCKED는 필요한 확인을 진행했으나 환경·증거 부족으로 해당 항목을 판정할 수 없는 경우다. 한 항목이 막혀도 전체 작업을 자동으로 중단하지 않는다.
