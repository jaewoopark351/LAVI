Coverage does not mean public exposure. Existing source, parser, admission,

The raw GUI path remains a separate authority tier.
`FabricChatClefCommandController`

raw-GUI adapter uses a closed feedback-only decoder before send to prepare an immutable
descriptor, then binds it only inside the existing accepted active-owner
transaction after server admission succeeds. This prevents a fast terminal
from racing tracker creation. The decoder must prove one of the 26 registered
profiles and the available typed slots, grants no execution authority, does
not replace Korean admission, and does not turn arbitrary raw text into a
trusted profile. If the decoder proves a registered command name
but cannot recover all richer slots, the accepted command may receive one
bounded command-profile acknowledgement and a cautious terminal that names
neither a target nor a success effect. If even the registered name is not proven, it
receives zero new lifecycle feedback. In both cases existing raw
execution/result behavior is unchanged.

| Tier | Scope | Rule |

| A | Current public Korean commands | Full natural feedback is required, subject to per-command evidence. |
| B | Remaining registered commands submitted through an existing LAVI direct-user policy, or a currently transport-accepted raw-GUI path whose name is proven by the new feedback-only decoder | Keep execution authority and safety/confirmation unchanged; bind a typed or command-name-only cautious profile only inside accepted ownership. |

## 3. User-visible lifecycle contract

The lifecycle model exposes up to three independently gated response
boundaries. Immediate and continuous profiles may not expose every boundary:

```text
accepted submission + designated owner committed
    -> one START response

user asks a status question + matching authoritative active evidence
    -> one STATUS response for that question, zero command submissions

matching terminal accepted by its designated result lane + first terminal CAS
    -> one truthful TERMINAL response
       -> strong success wording only with command-specific outcome/effect proof
       -> otherwise cautious, failed, cancelled, deadline, or unknown wording
```

For the motivating request, the generalized implementation must preserve:

| Boundary | Response body |
| --- | --- |
| Accepted `get diamond_pickaxe 1` from a validated craft request | `다이아 곡괭이 만들어 줄게` |
| Matching authoritative running evidence when the user asks | `다이아 곡괭이 만드는 중이야` |
| Matching completion plus authoritative acquisition delta | `다이아 곡괭이 다 만들었어` |

Changing only the item produces the same lifecycle grammar. For example,
`철 곡괭이 만들어줘` may produce `철 곡괭이 만들어 줄게`,
`철 곡괭이 만드는 중이야`, and, only after verified acquisition,
`철 곡괭이 다 만들었어`. No item-specific Python class or Java projector
constant may be required for each target.

The literal `[Minecraft]` marker is not part of a natural response body and
must not be spoken by TTS. The UI must render Minecraft as a separate source
badge or channel decoration. At this historical pre-change checkpoint that
badge path was `UI_BADGE_REQUIRED_NOT_IMPLEMENTED`; the generalized
implementation has since wired and focused-tested typed UI-only metadata
independently from speech.

## 4. Truth model

### 4.1 START means accepted ownership, not gameplay progress

A START response may publish only after all applicable conditions hold:

1. The input is a LAVI-owned interactive ingress permitted by the selected
   command/source profile; native ChatClef prefix and Butler ingress are not
   inferred from a Java command string.
2. On a registry-governed Korean ingress, parsing, command registry, source,
   safety, confirmation, target, and numeric admission all succeed. On raw
   `lavi_gui`, the unchanged transport admission succeeds and the closed
   feedback-only decoder proves a registered command/form and only the
   effective slots it can recover. That decoder grants no registry, safety, or
   confirmation authority.
3. The exact command submission is accepted by its existing route.
4. The same command identity and immutable feedback context are atomically
   committed to the command's designated lifecycle owner.
5. The path wins its one-shot START publication permit.

For ordinary tasks, including STORE_HOME submission, the designated owner is
the existing active-command owner under the existing `command_lock`. STOP alone
has an established specialized control tracker. STORE_HOME has an existing
typed Java projection and Python validator/renderer, but no dedicated Python
asynchronous terminal tracker or status inspector; it needs a general terminal
publication adapter over ordinary ownership. Immediate/settings routes and H5
automatic trust may expose an acceptance receipt, but they do not thereby gain
a dedicated terminal owner. Translation success, request-ID allocation, socket
send attempt, or an uncommitted local context is not enough.

`만들어 줄게`, `장착할게`, or `갈게` is an acknowledgement of accepted
responsibility. It is not a claim that Java has already started mutating the
world.

### 4.2 STATUS is read-only and on demand

The status path recognizes deterministic questions such as:

```text
마크 지금 뭐 하고 있어?
마크 뭐 만드는 중이야?
다이아 곡괭이 만들고 있어?
철 10개 구하는 중이야?
Steve 따라가는 중이야?
마크 지금 어디로 가고 있어?
```

The existing emergency STOP decision remains before status routing. A candidate
that the STOP safety boundary owns must not be reinterpreted by a weaker status
fallback. A non-STOP status question is handled before ordinary busy rejection.

Some Korean questions containing an exact STOP token are currently classified
as `GUARDED_STOP_LIKE_REJECTION`. The general status route must never reclaim
that decision. If a future STOP-status question such as `중지하는 중이야?` is
supported, the STOP owner itself must add a closed, read-only question outcome
that is disjoint from the imperative command grammar. Otherwise the user can
ask the generic `지금 뭐 하고 있어?` form. Both cases submit zero commands.

Within the designated synchronization boundary, status routing reads the
active owner, immutable response context, and latest accepted lifecycle
evidence together. It submits no command, retries nothing, changes no timeout,
and mutates no Minecraft, Task, input, goal, path, or diagnostic state. One
question may claim at most one STATUS publication permit.

An unqualified generic question must contain the validated `마크` or
`마인크래프트` addressee. A prefixless target-qualified question may be owned
only when its resolved family and complete typed target match exactly one live
active descriptor; otherwise it falls through without claiming a status
response. This prevents ordinary conversation such as `지금 어디로 가고
있어?` from being captured by the Minecraft route.

`CommandStatusQuery` also preserves a closed `requested_family`. `마크 뭐
만드는 중이야?` is craft-family-specific, whereas `마크 지금 뭐 하고
있어?` is `ANY`. An addressed family mismatch may truthfully say, for example,
`만드는 건 아니고 좌표로 가는 중이야` when movement is proven. A
prefixless family mismatch falls through with zero response and zero
submission; it cannot relabel the active command.

The natural “중이야” form is allowed only when the command profile accepts the
exact lifecycle reason as proof of active work. A generic `status=running`, a
callback that ended without a matching user Task event, quiescence observation,
or stale owner snapshot is not universally sufficient. A profile without an
approved progress predicate uses a cautious response instead.

| Observed state | Required response class |
| --- | --- |
| Matching, command-approved active evidence | Natural profile-specific `… 중이야` |
| Accepted but dispatch/start is not yet proven | `… 시작됐는지 확인 중이야` |
| No tracked LAVI command owner is present | `지금 내가 처리 중인 마인크래프트 명령은 없어` |
| Missing, stale, disconnected, quarantined, or contradictory evidence | `지금 작업 상태를 확인하지 못했어` |
| A validated `마크`/`마인크래프트`-addressed question names a target different from the active context | State the actual active work, or say the requested target is not the active work; never submit it. A prefixless mismatch falls through with zero response and zero submission. |

Repeated questions may each receive one fresh answer. They do not create a
second START or TERMINAL response.

Absence of the Python ordinary owner does not prove that untracked ChatClef,
manual-player, background-maintenance, or another Minecraft action is idle.
The broader sentence `지금 하고 있는 마인크래프트 작업은 없어` is allowed
only if an authoritative global-idle observer is separately implemented. A
missing feedback tracker alone is `UNAVAILABLE`, not global idle.

### 4.3 TERMINAL separates transport completion from outcome proof

Before any terminal sentence is eligible, exactly one designated result lane
must accept the result. For an ordinary command,
`accept_result_and_reconcile()` proves the active websocket object, session ID,
connection generation, request ID, correlation/message ID, and before-snapshot
owner identity. It does not echo or validate parsed command slots. The same
owner token must therefore also resolve to the immutable descriptor that was
atomically bound at admission; that second proof supplies command name and
typed slots. A wire result alone cannot reconstruct them. The first winner of
the lane's lifecycle-scoped terminal CAS is the only path allowed to publish.

For ordinary task-backed commands, the designated transaction is the existing
`accept_result_and_reconcile()` path and its before-snapshot owner check. For
the trusted marked `stop_control_v1` profile, it is the existing STOP result
demultiplexer, closed profile validator, tracker, and barrier transition; that
STOP result must not be sent through the ordinary terminal narrator. A
markerless raw-GUI/legacy `command=stop` deliberately remains on the existing
ordinary technical path. It cannot emit strong `멈췄어`; a future registered-name
raw adapter may provide only command-level cautious wording until the request
is separately migrated through the specialized control contract. An immediate
or settings command needs its own source-proven acceptance/commit profile
before terminal feedback is enabled. STORE_HOME continues through ordinary
correlation and then its typed operation-specific payload validator.

For an ordinary task, `status=completed`, `matching_task_finished`, and
`callback_plus_matching_user_task_event` together provide the strongest current
execution-closure association. Specialized and immediate profiles use their
own closed lifecycle evidence instead. Neither form by itself proves an item,
movement, transfer, setting, scan, or victory effect. A natural success
sentence is selected only after the command's effect/outcome evaluator accepts
its typed evidence.

If lifecycle completion is accepted but the expected effect cannot be proved,
the response remains natural but cautious, for example:

```text
다이아 곡괭이 만드는 작업은 끝났는데, 다 만들어졌는지는 확인하지 못했어
이동 작업은 끝났는데, 도착했는지는 확인하지 못했어
전달 작업은 끝났는데, 제대로 전달됐는지는 확인하지 못했어
```

Failures, cancellation, deadline expiry, disconnect, and UNKNOWN use separate
truthful outcomes. None triggers LLM recall, automatic retry, replay, command
resubmission, or a new tracker.

A deadline result does not prove that a Java Task has stopped, and a failure or
cancellation does not prove that every partial gameplay effect was rolled back.
The response describes the known lifecycle outcome only; cleanup/retirement
needs its own typed evidence.

### 4.4 Lifecycle-kind terminal predicates

There is no universal `completed` predicate:

| Lifecycle kind | Minimum terminal closure before outcome/effect proof |
| --- | --- |
| Finite ordinary Task | Exact ordinary reconciliation plus `completed`, `matching_task_finished`, and `callback_plus_matching_user_task_event`. |
| Immediate/query/settings with no long-lived user Task | Exact owner reconciliation plus `completed`, `callback_completed_without_user_task`, `callback_without_user_task`, and a typed result/readback. A pre-existing unchanged idle root remains UNKNOWN. |
| `follow`, `idle`, `hero` | No finite success. Only proven active, explicit stop, cancellation, failure, or cautious exit wording. |
| Long-running finite `gamer` | Exact BeatMinecraft root completion plus a typed source-bound victory projection; arbitrary Task exit or cancellation is not victory. |
| STORE_HOME | Finite ordinary reconciliation, strict outer terminal validation, and the closed STORE_HOME payload invariants. |
| Trusted marked STOP-control | Dedicated STOP demultiplexer, closed terminal profile, barrier plus applicable retirement or closed no-target/no-LAVI-context proof, and STOP-owned publication; never ordinary reconciliation. Markerless legacy/raw STOP remains ordinary and cannot claim this success. |

Outcome/effect evaluation follows closure and cannot weaken it.

For GET, the original validated request-action family is immutable context.
`craft` wording may describe the requested craft intent, while a mining verb in
the request does not prove that the physical acquisition route was mining. An
item-count delta without a route oracle therefore uses neutral `구하는 중이야`
and `다 구했어` wording. `캐는 중이야` and `다 캐 왔어` require a separate
same-operation mining-route oracle. Recipe, pickup, trade, and other routes are
likewise never inferred from the user's verb alone.

as request-fulfilment vocabulary: the accepted craft-worded GET request ended
with the required acquisition delta. It is not diagnostic proof that a
crafting-table or recipe route was physically used. Any UI or diagnostic claim
about that route still requires a separate route oracle.

For the currently registered `GetCommand`, every accepted count is an additive
request because `GetCommand#getItems()` applies
`AgentCommandUtils.addPresentItemsToTargets()` before constructing the Task.
Quantity one may be omitted where Korean is more natural, while a quantity
greater than one must be preserved exactly. A future `ENSURE_TOTAL` profile is
allowed only after a separate typed ingress and execution contract actually
introduce that meaning; it must not be inferred from the current raw wire form.
Here `{quantity}` is a renderer-owned token that is either empty or a complete
spaced phrase such as `3개 `. It prevents quantity-one omission from leaving
double spaces or joining a numeral to the following verb.
`{goal_quantity}` is reserved for such a future typed total-goal profile and is
not emitted for the current registered raw `get` command.

### 5.4 Rejection, failure, and uncertainty

The renderer maps bounded typed reasons to natural Korean. It does not speak
wire enums, stack traces, raw exception messages, arbitrary command text, or
diagnostic payloads.

| Outcome | Example style |
| --- | --- |
| Admission rejected | `그 명령은 지금 실행할 수 없어` plus a safe mapped reason when useful |
| Busy | The profile's complete `active_body`, only when active state is proven |
| Failed after work began | The profile's complete `failure_after_start_body` |
| Failed before dispatch | The profile's complete `failure_before_start_body` |
| Cancelled | The profile's complete reason-specific `cancelled_body` |
| Deadline exceeded | The profile's complete `deadline_body` |
| Terminal lifecycle accepted, effect unknown | The profile's complete `effect_unknown_body` |
| Correlation or connection uncertain | `작업 결과를 확인하지 못했어` |

A renderer never appends Korean fragments to one generic `{action}` stem. Each
profile supplies complete inflected lifecycle forms or selects from a closed
verb-form enum. The particle renderer separately handles final-consonant
rules, ASCII/player names, and numerals, with a deterministic fallback when
pronunciation cannot be inferred. Exact Korean snapshot tests cover every
phase so constructions such as `중이야 중이야`, invalid particles, or joined
quantity/verb text cannot ship.

### 6.1 Additive effect payload contract

`CommandResultDTO.data` already permits additive evidence, so this design does
not require a new top-level message type, result status, or protocol-v1 version.
It does require a closed profile schema so future command fields cannot be
mistaken for the current flat GET keys or for STORE_HOME/STOP payloads:

```text
effect_profile_id=<closed stable profile identifier>
effect_profile_version=<positive supported integer>
effect_kind=<closed family kind>
effect_payload=<bounded profile-specific map>
```

The decoder uses this closed precedence and never falls through from a malformed
specialized claim to generic success:

```text
1. STOP candidate marker/request_kind -> dedicated STOP validator
2. operation=store_home or store_home_result present -> STORE_HOME validator
3. any new-profile marker present -> new effect-profile validator
4. no new-profile marker + effect_kind=get_acquisition_delta -> legacy GET adapter
5. otherwise -> no-effect/cautious terminal
```

A new-profile candidate is any map containing at least one of
`effect_profile_id`, `effect_profile_version`, or `effect_payload`. It must then
contain all three plus `effect_kind`; partial, unknown, or unsupported claims
fail closed. A legacy GET candidate contains none of those three markers and
uses only the closed flat effect fields `effect_kind`, `target_item`,
`requested_count`, `before_target_count`, `after_target_count`,
`target_count_delta`, `effect_observation_status`, and
`effect_observation_reason`. Exact integer fields reject booleans.

A generalized GET `effect_payload` carries exact `quantity_semantics` and the
matching `requested_delta`; it must agree with the immutable descriptor.
Missing semantics or a delta mismatch fails closed. `wire_goal_count` remains
reserved for a future separately typed `ENSURE_TOTAL` contract and is forbidden
for the current registered `GetCommand`. The legacy flat GET adapter is
restricted to the exact diamond craft-intent `ACQUIRE_DELTA` compatibility
profile and is not reused to invent a different raw meaning.

Each profile declares exact required, optional, and forbidden fields and their
types. Unknown profile/kind/version, missing fields, duplicate contradictory
representations, or extra identity that disagrees with the immutable request
context fails closed to a cautious terminal. The existing exact flat GET fields
remain readable through a transitional compatibility adapter until migrated.
If a migration result temporarily carries both the flat GET representation and
`effect_payload`, every overlapping value must agree exactly or the evidence is
rejected. The schema fixes per-profile entry, list, string, and numeric bounds;
it carries no raw NBT, chat text, exception text, logs, or unbounded inventory
dump. It is not a template to mix unrelated family keys in one untyped map.
Projection decorates results only and does not change status, Task
selection/completion, retry, timeout, input, goal, path, or cleanup.

The extension currently mirrors the same result data into `status.data` and
`details`. If either location claims a specialized or general effect profile,
all claimed representations must be schema-valid and agree field-for-field;
one valid copy cannot mask a malformed or contradictory copy. A Java map being
JSON-serializable is not validation, so focused Java-to-JSON-to-Python fixtures
are required for nested payloads, numeric types, bounds, and duplicate-copy
consistency.

Cross-family claims fail closed unless a later contract explicitly approves a
dual-profile schema. In particular, a STORE_HOME claim combined with any
`effect_profile_*`, `effect_payload`, or legacy GET effect marker is cautious/
rejected before the current STORE_HOME parser, which by itself ignores extra
keys. Specialized precedence must not become family-confusion permission.

### 6.2 Source discrepancies that block blind profile generation

The registry currently declares `gamer` with a `target` slot, while the Java
`GamerCommand` is argument-free. That drift must be characterized and corrected
in its own registry/source-contract change before feedback derives a label from
the slot. Similarly, `gamma` currently has no ordinary `finish()` call, so its
terminal cannot be documented as already available.

Closing a source discrepancy is not implicit permission to edit an
upstream-derived command or Task. Prefer a LAVI-owned observation/adapter that
preserves engine lifecycle. If `SetGammaCommand`, GIVE, or another upstream
behavior method is later proven to require a behavior hunk, that is a separate
engine-divergence scope subject to the ChatClef last-resort gate, exact rollback
record, and focused regressions; the feedback profile remains cautious until
then.

Raw Java grammar is also broader than the public Korean compiler: item commands
may accept single or bracketed `ItemList` forms, GOTO has additional target
forms, GIVE/FOLLOW have Java-specific defaults, and automatic trust has single
target and area forms. The immutable descriptor must be built by a grammar
owner appropriate to the accepted ingress. It must not split arbitrary text on
spaces and guess a profile.

## 7. Immutable request context

The response context is built from already validated values at the accepted
submission boundary. It contains only the fields needed by the selected
profile, including:

```text
command_name
lifecycle_kind
form_kind=<closed command-specific grammar form>
intent_type, when available
validated action/verb family
typed_slots=<closed immutable command-profile value object>
targets=<ordered immutable tuple of
  canonical_target,
  match_set_or_profile_id,
  quantity_semantics=ACQUIRE_DELTA|PROFILE_SPECIFIC_UNITS,
  requested_delta_or_null,
  wire_goal_count_or_null,  # reserved; null for every current GetCommand form
  profile_specific_units_or_null,
  bounded_korean_label,
  slot_provenance=explicit|defaulted|butler_derived|crosshair_derived|live_inventory>
validated player, coordinates, structure, setting, or destination slots,
  when those are not target entries
trusted input provenance
websocket/session/generation/request/message identity
submission/publication sequence
effect-profile identifier
```

A single-item request has one `targets` entry; an accepted bracketed raw form
retains every target in source order. The descriptor never collapses a
multi-target request into one noun. If two entries have overlapping match sets,
for example `log` and `oak_log`, one observed inventory delta cannot be counted
twice. Strong success requires an explicit operation-bound allocation oracle;
without it the whole terminal remains cautious.

The current Korean and raw ChatClef `get target N`/`ItemList` paths both use
`ACQUIRE_DELTA`; this is source-proven by the registered `GetCommand`, which
adds present inventory counts before dispatching its acquisition Task. A future
total-goal ingress must use a distinct `ENSURE_TOTAL` descriptor and numeric
field rather than changing the meaning of the current wire form. A descriptor
with missing or contradictory quantity semantics fails closed to command-level
cautious wording.

Java-only defaults and derived values are not guessed in Python. A missing
GIVE/FOLLOW player, bare DEPOSIT target manifest, crosshair-derived automatic
trust destination, default GAMMA/SCAN argument, or similar slot may enter a
target-specific phrase only after a typed effective-slot receipt binds that
value to the same request. Before that receipt, the profile uses a
command-name-level acknowledgement and cautious terminal.

The context is immutable after ownership commit. Terminal rendering never
calls the LLM, reparses the original sentence, consults mutable conversation
history, or reconstructs identity from a command string. Direct typed commands
do not currently have a general raw grammar parser: the registry's
`serializer_id` is metadata, not recovered slot evidence. Korean ingress may
reuse its validated intent/compiler values. Raw or direct forms require a new
closed grammar decoder or a typed Java effective-slot receipt; without either,
only a command-name-level cautious profile is allowed.

phrases and does not import `response/`. The response facade owns phrase
selection and rendering, while application/extension composition joins those
two boundaries. The status classifier owns only question shape; semantic
target resolution and active-descriptor comparison belong to the separate
resolver and existing family-specific slot resolvers.

The phrase registry and terminal-evidence registry are separate closed
authorities. Both must have exact 26-command coverage, and tests must compare
the full `command -> lifecycle kind -> phrase profile -> evidence profile`
mapping, not merely the command-name set. An evidence profile explicitly says
`disabled`, `cautious`, or `verified`; registry metadata such as
`gameplay_effect_verifiable=get` is only a family hint and does not prove every
GET target.

Profile rollout state has this exact meaning:

| State | Allowed feedback |
| --- | --- |
| `disabled` | Zero new lifecycle feedback; preserve every existing technical/UI response. |
| `cautious` | Accepted START and separately proven STATUS are allowed; terminal wording may state only the closed lifecycle/non-success facts and never strong effect success. |
| `verified` | Same as cautious, plus strong terminal wording only when that profile's complete outcome/effect predicate succeeds. |

Changing this state never changes command admission, execution, retry, or
result handling. Generic acknowledgement suppression is part of the same
dispatch decision as selecting an enabled natural START permit: `disabled`, an
unproven decoder, or profile rollback preserves the existing acknowledgement;
an enabled winner chooses one natural acknowledgement and zero duplicate
technical acknowledgements.

The existing 468-line crafting tracker currently combines descriptor,
lifecycle, result, CAS, and publication responsibilities and must be split
behind compatibility ports during migration with single-boundary parity.
Prefer composition and explicit ports, not inheritance.

The existing command lock remains the single synchronization and truth boundary
for the ordinary active owner and its feedback tracker. Do not add a second
lifecycle/state-ownership lock, mutable singleton, or global tracker. A
permit-local `threading.Condition` may exist only for bounded publication wait
signaling; it owns neither command truth nor terminal CAS. Rendering and output
calls occur outside the command lock. START, each claimed STATUS answer, and
TERMINAL preserve FIFO order; timeout/shutdown must wake waiters, and a failed
publication retires only the permit/lifecycle defined by its existing failure
contract without deadlocking terminal delivery.

Existing admission-grant spend, publication-acknowledgement, terminal-listener,
and permit-local synchronization may remain for their narrow object-local
atomicity. None may become a second owner of ordinary lifecycle truth,
active-command identity, or terminal CAS. When terminal claim wins under the
command lock, it closes future STATUS-permit issuance and freezes the finite
predecessor publication sequence so repeated questions cannot starve terminal
delivery.

STOP retains its specialized tracker, correlation semantics, barrier, and typed
renderer. STORE_HOME retains ordinary active-command ownership plus its
existing Java typed result projection and Python validator/renderer; a new
general asynchronous terminal adapter must not be misnamed as an existing
specialized STORE_HOME tracker. Neither adapter merges STOP state into ordinary
lifecycle or reuses it for another command.

The current natural START hook exists only in the ordinary submission-result
stage. Generic-crafting-default submission and H5 automatic-trust routing have
separate stages. Each accepted route must adapt its own already-proven receipt
to the common facade; generalizing only the current admission authorizer would
still leave commands silent. On Java, `FabricChatClefCommandExecutionState`
currently holds the concrete `FabricChatClefGetItemEffectTracker` directly.
During generalization, migrate that field behind the planned generic effect
port/tracker selected by `EffectTrackerFactory`; do not add another
family-specific field alongside it or create a generic `operation/` catch-all
package. A new family folder is created only when its first concrete projection
exists.

## 10. Routing, delivery, and duplicate suppression

The interactive route order is:

```text
trusted Korean eligibility proof for the Python natural-language sequence
  -> exact emergency STOP ownership
  -> deterministic lifecycle-status question ownership
     (the current exact crafting-status owner is migrated here)
  -> scoped generic-crafting-default submission
  -> existing intent eligibility gate
  -> H5 automatic-trust routing
  -> ordinary command busy/admission handling
  -> unrelated conversation fallback
```

Each stage either owns the input once or falls through once. A status winner
submits zero generic-crafting, H5, ordinary, or raw commands; a STOP-owned
candidate never falls back to status. This preserves the reviewed
`STOP -> crafting status -> generic-crafting-defaults -> intent gate -> H5 ->
ordinary` precedence while replacing only the exact crafting-status owner with
the generalized read-only owner.

Raw `lavi_gui` does not enter this sequence. It keeps its direct
controller-to-`handle_command()` path; the feedback-only predecoder may prepare
a descriptor, but publication becomes eligible only if the existing server
admission and active-owner commit bind that descriptor atomically.

`lavi_gui_korean` likewise needs its own UI-event receipt before it may enter
the lifecycle-feedback composition. Its current source string does not
substitute for the trusted router proof, and the existing technical UI result
remains visible when no lifecycle receipt exists.

An eligible accepted command produces one natural START body. The current
generic `[Minecraft] … 명령을 제출했어요` body is suppressed for that same
accepted lifecycle so the user does not hear two acknowledgements. A cautious
or failure terminal likewise has one owner.

STOP control owns the user-visible stop terminal. The original ordinary
command's correlated `cancelled/user_stop_requested` result remains necessary
for reconciliation and audit but publishes no second cancellation sentence.
Before general rollout, characterize the current exact crafting/STOP race and
add one explicit publication-arbitration test; a generic `CANCELLED` branch must
not produce a second terminal publication/dispatcher invocation after the STOP
owner selects `멈췄어`.

Each claimed response permit invokes the existing output dispatcher at most
once. UI source decoration is separate. Response text is not appended as new
user input, is not routed back through intent extraction, and cannot recursively
submit a command. Output failure never changes Minecraft command success and
never authorizes replay.

The current stream payload does not expose a dedicated Minecraft badge field,
and `LLMEventDispatcher.send_output()` may isolate listener failures. Therefore
a dispatcher invocation or current publication acknowledgement does not prove
that audio was queued or heard. Implementation must add a bounded typed UI-only
source field and a presentation-sink receipt; it must not omit the required
badge or put `[Minecraft]` back into spoken text. Queue acceptance and playback
observation remain `NOT_PROVEN` until their distinct sink-owned receipts are
implemented and tested; exactly-once playback is never inferred from either
receipt alone.

An asynchronous/out-of-band TERMINAL lifecycle event never creates, advances,
cancels, or replaces the global LLM response generation. It carries a
command-local sequence and a `non_preempting` delivery kind. If the TTS sink
cannot receipt that contract, terminal lifecycle TTS stays `disabled` and only
the proven UI path may publish. If it can, the sink enqueues in command-local
FIFO order without interrupting the current or newer unrelated speech. START
and on-demand STATUS remain bound to the current input's capability-response
generation, with zero new LLM calls and zero recursive input. Add every new
lifecycle `route_kind`, `response_kind`, and delivery mode to the applicable
delivery/diagnostic allowlist so valid lifecycle responses are not mislabeled
as invalid. Where the same formatter records TTS sink or reason enums, their
new values require the same closed-set registration and test. A typed
asynchronous Chat presentation path and receipt are not currently
implemented/proven and are required for every surface expected to show the
Minecraft badge.

## 14. General implementation completion gate

The all-item/all-command request is complete only when all of the following are
true together:

1. Every actually callable LAVI Tier A/Tier B ingress has its required closed
   decoder, provenance receipt, and presentation adapter. This explicitly
   includes the raw `lavi_gui` registered-name/form decoder and the
   `lavi_gui_korean` UI-event receipt.
2. Every registered command accepted by any such ingress is `cautious` or
   `verified`; none is disabled or silently untracked.
3. Every accepted registered/profile-eligible request covered by item 2 has
   the complete response set for its lifecycle kind, with a presentation
   receipt for each publication: a finite asynchronous Task has START,
   authoritative on-demand STATUS, and the first accepted truthful TERMINAL;
   a persistent Task has START, authoritative active STATUS, and only a typed
   stop/failure terminal; a synchronous immediate/query/settings operation has
   one coalesced result or failure; and an asynchronous immediate operation has
   ordered START then TERMINAL. Effect-insufficient terminal evidence uses the
   cautious wording instead of omitting the response. An exact
   command-by-lifecycle-kind matrix test must prove this coverage.
   Unregistered, malformed, or genuinely ambiguous raw requests retain only
   their existing technical result and are not counted as lifecycle-feedback
   omissions. A syntactically valid accepted registered raw form covered by
   the closed decoder contract is a coverage failure if that decoder cannot
   recognize it.
4. Every admitted item/form, including dynamic raw domains, has a bounded
   Korean phrase or deterministic target-neutral fallback and typed UI detail.
5. All six source-known exact-slice closure gates are closed, and every new
   route adapter, effect-profile discriminator, UI badge, TTS receipt,
   non-preemption rule, and diagnostic allowlist test passes.
6. `disabled` is allowed only for a dormant registry row with no actual caller
   or for a command whose admission remains disabled by its existing policy;
   feedback state must never be used to hide an accepted silent route.
7. Focused and full Python/Java regression plus the required clean forced build
   pass for the exact source and artifact under review.

This gate changes no command's public exposure. It prevents registry-name
coverage alone from being reported as fulfillment of the user-visible request.
