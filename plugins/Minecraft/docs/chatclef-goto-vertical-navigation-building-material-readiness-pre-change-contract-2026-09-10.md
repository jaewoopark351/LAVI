### 5.4 Exact whole-route placement count is not currently available

The Baritone API interface `IPathExecutor` does not expose one stable count of
every block placement needed to reach the final GOTO target. The concrete
public `PathExecutor.toPlace()` implementation is observable after a path
exists, and current source reads it in `UnstuckChain.java:178-190`, but that is
an implementation-coupled snapshot of the remaining movements in the current
adopted path generation. It is not a stable public-interface contract.
Replanning, partial paths, path-position changes, and executor replacement can
change it.

A newly created executor also begins with an empty placement set and populates
it during path execution/recalculation. Without an added freshness boundary,
an observed zero can mean “not populated yet” rather than “computed and needs
no placement.” A positive set can support a fact about that exact current path
generation and position only; neither zero nor a later stale set proves the
whole route.

Moreover, when the effective acceptable placement set is empty, placement
movements may be excluded during path calculation. A current-segment
`toPlace().size() == 0` then does not prove that an otherwise feasible route
would need no blocks. Diagnostics must report separate facts:

```text
currentPathGenerationToPlaceCount:
    IMPLEMENTATION_COUPLED_ADVISORY value or UNAVAILABLE
currentPathGenerationToPlaceFreshness:
    POPULATED_FOR_BOUND_GENERATION / NOT_PROVEN / STALE
wholeRoutePlannedPlacementCount: UNAVAILABLE
placementRequirement:
    CURRENT_PATH_GENERATION_PRESENT / NOT_PROVED / PUBLIC_API_UNAVAILABLE
```

This prevents an unavailable whole-route fact from being fabricated as zero.
It also required an explicit decision between a strict current-path-generation
observation mode and a separately bounded recovery heuristic after ordinary
navigation stalls. Section 8.3 records the selected public bridge mode and
keeps the strict task-level policy distinct.

### 7.2 A2 — exact arrival effect proof

A2 has two ordered owners. The route Task first makes a task-local terminal
decision from live state and freezes an immutable arrival-candidate snapshot:

```text

current dimension == resolved destination dimension

    == active GOTO operation

```

The Task must not wait for its own `TaskFinishedEvent`. `UserTaskChain` invokes
`onTaskFinish` and publishes that event only after the Task has already
finished. Requiring the event in `isFinished()` or the parent terminal
predicate would create a circular wait.

After task-local finish, the bridge-level GOTO result projector may publish
`ARRIVED` only when all of these later facts agree:

```text

matching natural TaskFinishedEvent refers to the same GOTO root instance
event observation occurs after the candidate snapshot
snapshot, TaskFinishedEvent.lastTaskRan, authoritative completion envelope, and
bridge command ledger agree on the frozen root object reference,
rootAssignmentId, rootGeneration, request/session/correlation,
```
