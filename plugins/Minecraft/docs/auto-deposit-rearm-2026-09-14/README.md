# 자동보관 종료 후 재실행 설계

## 목적과 현재 상태

자동보관으로 공간을 확보한 뒤 인벤토리가 다시 차도 `WAIT_FOR_REARM`에서 벗어나지 못하는 문제를 다룬다. 정상적인 다음 정리는 허용하고, 실패한 보관·상자·재료 확보의 무한 반복은 막는다. **자동방어는 자동보관보다 항상 우선하며, 기존 공격·회피·무기 선택과 생존 동작·먹기를 유지한다.**

2026-09-14 사용자가 전달한 ChatGPT 검토를 당시 소스 및 기존 실행 로그와 대조한 뒤 문서화했다. 이후 사용자가 이 설계의 **구현을 직접 요청**하여 저장소 안의 구현·테스트·검증 작업을 진행하고 있다. 외부 검토문 자체를 작업 권한으로 취급하지 않는다.

이 문서는 앞선 금 채굴 구현이나 진단 전용 작업의 결과를 대체하지 않는다. 기존 346개 Java 테스트 통과와 1.20.1 빌드는 이전 소스의 증거이며, 이 새 설계가 검증됐다는 뜻이 아니다.

최종 검증은 [2026-09-14 03:33:06 실행](../../../../logs/auto_deposit_1201_Build_20260914_033306_455/verification.log)을 사용한다. 이번267개는 선택한 자동보관 회귀 집합의 결과이며 이전346개 기록과 실행 범위가 같다는 뜻이 아니다. 정확한 명령·브랜치·HEAD·입력 manifest와 새 JAR의 SHA-256은 [구현 기록](implementation.md#최종-실행과-입력산출물-식별)에 연결했다. 게임에서 인벤토리 재충전·방어·회수·보관을 실제로 확인하는 단계는 남아 있다.

## 확인된 문제

```text
33칸에서 5칸 확보 계획
  → 준비 중 35칸
  → 전송 후 30칸
  → 시작 대비 순감소 3칸: PARTIAL_RELIEF
  → DONE → WAIT_FOR_REARM
  → 다시 33칸·36칸이어도 새 계획 미평가
```

전송 전후 비워진 소스 슬롯 5칸과 시작 대비 순감소 3칸은 서로 다른 값이다. 재실행을 허용하려고 `actualFreedSlots=3`을 5로 바꾸거나 FULL_RELIEF로 위장하지 않는다.

수정 전 WAIT는 점유 28칸 이하 또는 등록된 신뢰 보관소 revision 변경으로만 해제된다. 이번 `PARTIAL_RELIEF→DONE`의 종료 점유 30칸은 이 조건을 충족하지 않으며, Idle과 시간 경과도 해제 조건이 아니다. 이 DONE 기록만으로 새 설계가 요구하는 자식 결과·필수품·cleanup까지 모두 유효한 정상 완료라고 확정하지 않는다. 마지막 직접 자동보관 판정은 **00:49:28**이다. 이후 Heartbeat를 내부 상태의 새로운 관측으로 사용하지 않는다.

## 수정 방향

정상 종료 결과에 자기 트리 cleanup 뒤 다시 확인한 점유와 필수품 상태를 전달한다. cleanup 전 후보는 불변으로 보존하며, cursor 물품 복귀 등 cleanup 중 변화를 최종 결과에 반영한다. 33칸 미만까지 여유가 회복됐다면 이후 33칸 이상을 새로운 정리 기회로 처리한다. 기존 low-water인 28칸 이하도 포함하며 끝난 압력 과정의 소진량만으로 새 수요를 막지 않는다. 정리 후에도 33칸 이상이면 같은 압력 구간에서 제한된 후속 계획을 평가한다. 실패·무진척·관측 불가·안전 선점·STOP은 별도로 다룬다.

실제 실패·무진척·후속 실행 제한은 기존 자동보관 Runtime/PressureChain 소유 경계에서 유지한다. 자식 Task·새 계획·Idle·명령·단축바 변경으로 기록을 초기화하지 않는다. 필요한 물품 보호와 신뢰 보관소 구분, 수동 보관 우선권은 유지한다.

정상 완료 후 재상승과 실패 원인이 개선된 경우는 서로 다른 재평가 경로다. 정상 재상승마다 개별 아이템의 외부 획득 증명을 요구하지 않는다. 실패 후 28칸 이하가 된 경우에도 공간 부족의 해소와 실패 목적지·STOP·소진 한도의 해제를 구분한다. 특정 상자 실패가 다른 유효한 상자까지 모두 막지 않도록 원인·목적지 범위를 유지한다.

방어가 선점하면 보관이 양보하고 안전해진 뒤 현재 위치·인벤토리·보관소로 계획을 재평가한다. **방어 중단은 보관 실패를 추가하지도, 기존 실패를 지우지도 않는다.** 방어 전 실제 무진척은 유지하고 방어 대기 시간은 제외한다. 위험이 계속돼 기다리는 것과 안전해졌는데 선점 횟수만으로 재개를 막는 것은 구분한다.

같은 정리를 방어 후 재개할 때는 원래 시작 점유와 확정 기록을 유지하되 개별 Task 세대를 구분한다. 이미 확보한 공간을 잃어버리거나 이전 결과를 중복 반영하지 않는다. 정리를 마친 뒤 별도로 허용한 후속 단위는 새 시작 점유를 사용하며, 압력 과정의 제한은 유지한다.

중단 전에 정산된 필수품은 이후 방어의 음식 소비 때문에 과거 보관의 부족으로 바꾸지 않는다. 원래 예약의 실제 부족이 남았다면 보관 출처와 필수품 snapshot을 유지한 **새 회수 전용 root**로 먼저 회수한다. 회수 뒤 `REPLAN_REQUIRED`로 넘겨 현재 계획을 다시 평가하며, 옛 슬롯 자식을 되살리거나 회수 자체를 새 보관 성공으로 세지 않는다. 확인된 회수량과 저장량은 따로 기록하고 실제 회수 실행도 같은 실행·무진척 한도를 사용한다.

음식·장비 수량의 의미 있는 증가는 현재 보호 정책을 통과한 surplus와 합계 증가로 확인한다. 착용·손 교체·내구도 변화·음식 소비만으로 실패를 풀지 않는다. 목적지 실패는 음식이나 무기 변화가 아니라 해당 목적지 조건으로 재확인한다. 명시적 STOP이나 사용자 root 교체로 옛 정리 단위를 취소해도 이미 소비한 한도와 실패 이력은 지우지 않는다.

실제 필수품 부족으로 끝난 경우에는 실패한 **원래 예약 전체의 복구**를 별도로 관측한다. 같은 월드·차원·사용자 root에서 main+cursor 수량을 비교하므로, 현재 계획이 요구량을 줄였다는 이유로 복구됐다고 판단하지 않는다. 보호된 음식·장비의 원래 부족분이 모두 복구되면 제한적으로 다시 확인하며, 일부 회복이나 무관한 목적지 실패까지 해제하지 않는다.

같은 월드에서 사용자 root만 바뀌어 원래 부족 예약의 복구를 증명할 수 없으면 `UNKNOWN_CONDITION`으로 대기한다. 이를 실패 해소·한도 초기화·추가 허가 근거로 사용하지 않으며, 월드 교체에 따른 기존 컨텍스트 초기화와 구분한다.

보관 cleanup은 방어가 선택한 무기·입력·경로를 되돌리거나 취소하지 않는다. 재개 시에도 STOP·수동 보관·현재 작업의 필수품 보호를 확인한다. “지금 행동해도 되는가”와 “다시 실행할 근거가 있는가”를 기존 대기 이유와 실제 결과에서 나누며 불필요한 관리 계층은 추가하지 않는다.

**기존 초안의 총 root 등록 2회와 안전 재개 평가 횟수 소진으로 차단하는 제안은 철회했다.** 제한 대상은 방어 양보 횟수가 아니라 실제 보관 기회에서 반복되는 실패·무진척과 동일 정리 과정의 후속 실행이다. [미확정 설계 항목](design.md#미확정-설계-항목)의 후보 결정과 남은 검증은 [구현 기록](implementation.md)에 연결한다. 소스의 초기 한도는 런타임에서 조정·검증된 수치가 아니다.
