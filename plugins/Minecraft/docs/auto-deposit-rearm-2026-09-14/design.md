## 바꿀 계약과 보존할 계약

기존 StateMachine 테스트는 실행 종료 뒤 32칸을 관측해도 WAIT를 유지하고 28칸에서만 재무장한다. 이 기대값 전체를 삭제하는 대신, 정상 정리와 실패·중단의 계약을 분리한다.

바꿀 계약은 다음 두 가지다.

1. 정상적인 자동보관 뒤 실제 여유가 회복되어 33칸 미만이면, 나중에 다시 차는 인벤토리를 처리한다.
2. 일부 정리했지만 여전히 33칸 이상이면, 같은 압력 구간의 남은 한도로 후속 정리를 검토한다.

33/36 발동 기준과 28/36 low-water 경로는 보존한다. LOW_WATER를 32로 일괄 변경하거나 모든 종료를 즉시 ARMED로 바꾸지 않는다. 28 이하도 STOP·비활성화·유효하지 않은 세션을 우회하는 해제 수단으로 쓰지 않는다.

`DONE`은 Task 수명 종료이며 성공 증명이 아니다. 슬롯 순감소, 전송 관측, 자식 성공, 필수품 유지, 소유 Task 정리 결과를 서로 대체하지 않는다.

## 종료 결과를 동작에 전달

아래 구분은 기존 소유 경계의 의미를 명시하며 새 관리 계층이나 상태 enum을 요구하지 않는다.

| 범위 | 방어 재개와 후속 정리에서 유지할 것 |
| --- | --- |
| 같은 압력 과정 | 공간 부족을 처리하는 전체 과정의 실제 실패·무진척·후속 실행 제한. 여러 정리 단위와 방어 대기를 포함 |
| 한 정리 단위 | 하나의 정리를 완료하려는 목적과 그 시작 pressure. 방어로 root를 다시 만들어도 유지. 그 정리를 마친 뒤 별도 후속 정리를 허용하면 후속 단위에는 실제 새 시작 pressure를 사용 |
| 개별 실행 root | 재생성될 때 구별되는 세대와 그 root에서 실제 관측한 값. 이전 root의 늦은 콜백이 재개 root를 완료시키거나 결과를 덮어쓰지 못함 |

같은 정리 단위를 재개하기 전에 이전 root에서 이미 확정한 진척·실패·누적량을 소유 경계에 한 번만 보존한다. 원래 시작 pressure를 재개 시점 값으로 초기화하지 않으며, 각 root의 원래 관측값도 덮어쓰지 않는다. 정리 단위의 순변화는 원래 시작과 최종 종료를 비교한다. 별도 후속 단위에서 이전 정리의 감소량을 다시 이번 진척으로 세지 않고, 압력 과정 전체의 제한은 계속 유지한다.

`maintenance/result/AutoDepositRunResult` 같은 불변 결과로 정상 게임 코드에서 확보한 값을 전달한다. 최소 정보는 다음과 같다.

| 정보 | 의미와 부재 처리 |
| --- | --- |
| 정리 단위의 결합, root generation, world/session identity | 같은 목적을 이어 가는 것과 같은 root인 것을 구분. 이전 root·월드의 늦은 결과는 재무장/새 결과를 덮어쓰지 않음 |
| terminal reason | 정상 종료, 자식 실패, 안전 선점, STOP, 비활성화, context 변경, 한도 소진, 관측 불가를 구분 |
| 시작·종료 pressure snapshot | 정리 단위의 원래 시작·최종 종료와 개별 root 관측 범위 구분. 유효 여부, main 인벤토리 범위, totalSlots, 관측 시점 보존. 범위 불일치는 유효한 비교가 아님 |
| 부호 있는 순변화 | 결합된 범위의 `시작 점유 - 종료 점유`. 기존 개별 실행의 `actualFreedSlots=max(0, 순변화)`를 사후 덮어쓰지 않고 정리 단위의 비교를 별도로 전달 |
| 기존 slot-relief 분류 | 유효한 관측에서 FULL/PARTIAL/NO_SLOT_RELIEF 의미 유지. UNKNOWN을 NO_SLOT_RELIEF로 위장하지 않음 |
| working-set 결과 | 검증 완료, 부족, 조회 불가, 정상 Idle로 적용 대상 없음 구분 |
| 자식 결과·전송 진척 | 기존 동작 소유자가 제공하는 실제 결과만 사용. 없는 값은 UNKNOWN. 진단 이벤트를 다시 읽지 않음 |
| cleanup 결과 | 이 실행의 소유 트리가 정리됐는지 및 실패 이유. 공간이 생겨도 cleanup 실패를 정상 완료로 표시하지 않음 |

정상 relief 기반 재무장에 필요한 값은 종료 원인, 동일 실행에 결합된 유효한 pressure 비교, 필수 자식의 완료 계약, working-set의 충족 또는 명확한 비적용, cleanup 결과다. 이 필수 정보가 UNKNOWN이면 정상 재무장으로 보내지 않는다. 반면 추가 전송 상세나 서버 ACK가 미관측이라는 사실만으로 정상 동작 소유자가 확인한 완료를 취소하지 않는다. **필수 판단 정보의 조회 불가와 선택적인 상세 증거의 부재를 구분**하며, 기존 DONE 하나로 필수 완료 정보를 대신하지도 않는다.

방어 선점으로 끝난 개별 Task의 결과와 같은 보관 목적의 실패 기록도 구분한다. 방어 중단 시 슬롯 수가 그대로라는 사실만으로 NO_SLOT_RELIEF 실패를 추가하지 않는다. 중단 전에 동작 소유자가 이미 확정한 실패·진척·무진척은 별도로 보존한다.

현재 verifier는 snapshot 읽기 실패 때 시작 점유를 종료 점유로 대신하고 NO_SLOT_RELIEF를 반환한다. 재무장 입력으로 확장할 때 관측 상태/Optional snapshot을 추가해 실제 무진척과 조회 불가를 분리한다. 실패를 0칸 보유·0칸 진척으로 가정하지 않는다.

현재 Maintenance는 trusted child의 finished/stopped, general child의 stopped도 다음 단계로 진행시킬 수 있다. RECOVER 뒤 남은 deficit도 별도로 존재한다. 이 상황에서 outcome 필드만 읽어 성공 기반 재실행을 허용하지 않는다. 기존 자식의 typed 결과가 제공된다면 연결하고, 부족한 정보는 UNKNOWN으로 보존한다.

### 결과 캡처와 정리 순서

`SingleTaskChain`은 finished와 stopped 모두 `onTaskFinish`로 전달할 수 있고 `setTask(null)`은 기존 Task.stop을 호출한다. 다음 순서가 필요하다.

1. 정상 동작 소유자에서 실제 종료 원인과 종료 pressure를 캡처하고 해당 run에 결합한다.
2. 소유 Task/입력만 정확히 한 번 정리한다. never-ticked root, 이미 stopped인 자식도 구분한다.
3. 정리 결과와 우선하는 외부 제어를 반영해 최종 결과를 한 번 확정한다. 정상 종료 후보가 cleanup callback 때문에 무조건 CANCELLED가 되거나, 정리 실패가 정상 완료로 바뀌지 않는다.
4. 결과를 상위 정책에 전달하고 상태를 전환한다. 이후 Idle·다음 Task·플레이어 이동으로 과거 종료 snapshot을 수정하지 않는다.

다음 tick에 우연히 30칸을 다시 관측할 것이라고 가정하지 않는다. 종료 30칸, 다음 pressure 관측 33칸인 경우에도 실제 종료 snapshot을 기준점으로 사용한다.

예를 들어 `정리 시작36→보관32→방어→재개32→정상 완료32`에서 마지막 root만 보면 순변화는 0이지만 같은 정리 단위는 4칸 감소했다. 자식 완료·필수품·cleanup 등 정상 조건까지 유효한 회귀 입력에서는 재개 root의 0만으로 전체를 NO_SLOT_RELIEF로 처리하지 않는다. 이 예시는 과거 로그에서 새로 확인한 사건이 아니며, 실패나 조회 불가를 정상 완료로 바꾸는 근거도 아니다.

## 재실행 상태 전이

제어 허용, 유효한 세션, 소유 Task 정리, 수동 보관 충돌과 안전 조건을 먼저 확인한다. 아래 표의 “정상”은 단순 DONE이나 슬롯 감소만이 아니라 해당 실행 결과의 유효성을 뜻한다.

| 입력 | 제안 전이/동작 |
| --- | --- |
| 최초 ARMED + 33칸 이상 | 기존 보호·충돌·계획 검사를 거쳐 READY일 때 최초 실행 1회 |
| 정상 종료 + 유효한 종료 점유 28 이하 | 기존 low-water 재무장 경로로 다음 압력 도달을 기다림. 이후 33칸 이상이면 새 압력 과정의 한도를 적용하며, 끝난 과정의 소진량만으로 차단하지 않음 |
| 실패/한도 대기 + 유효한 28 이하 관측 | 압력 해소를 기록하고 다음 재상승의 평가 자격을 회복. 실패 목적지·소진 실행 한도·STOP 해제는 별도 판단이며 이 관측만으로 충전하지 않음 |
| 정상 종료 + 실제 순감소 + 종료 29~32 | 성공 후 대기 상태 `WAIT_FOR_PRESSURE_RISE` 제안. 종료 snapshot을 보존하고 이후 33칸 이상에서 새 계획을 한 번 평가 |
| 부분 정리 + 종료가 계속 33 이상 | 같은 압력 구간의 남은 허가와 실행 한도에서 제한된 후속 평가. 현재 inventory/working-set으로 새 immutable plan 생성 |
| NO_SLOT_RELIEF / 자식 실패 / 한도 소진 | typed reason을 보존한 차단 대기. 같은 조건에서 즉시 재시작하지 않음 |
| 관측 불가/범위 불일치 | UNKNOWN/UNAVAILABLE. 정상 결과나 0 진척으로 변환하지 않음 |
| 자동방어·먹기·생존 선점 | 보관 소유 동작만 정리하고 안전 대기. 선점 자체의 실패·무진척 소비는 0. 안전 회복 뒤 현재 계획을 재평가하되 이전에 실제로 누적된 기록·제한은 유지 |
| STOP / 자동화 비활성화 | 제어 차단 유지. low-water, 등록 변경, 회복 허가도 실행을 강제하지 못함 |
| world/session 변경 | 이전 결과와 소유 작업을 무효화/정리. 새 세션 생성은 과거 성공과 별도 |

실패 사유마다 상태 enum을 무제한 늘릴 필요는 없다. 성공 후 재상승 대기처럼 전이 방식이 다른 상태와, 차단 원인을 나타내는 typed reason을 구분한다. 구체적인 enum 배치는 구현 경계에 맞춰 정한다.

`36→34`는 임계값 아래로 내려간 적이 없어 재상승 조건만으로 해결되지 않는다. 추가 정리가 현재 상태에서 효과가 있을지 평가하고 같은 압력 구간의 후속 실행·실제 무진척 제한을 유지한다. 물품 일부 전송이나 새 계획·자식 생성만으로 새로운 압력 구간을 만들지 않는다. 후속 평가가 READY여도 적용되는 실제 실행 한도가 소진됐다면 시작하지 않는다. NO_SAFE, 목적지 부재, 조회 불가면 평가 결과를 저장하고 다음 tick에 같은 계획을 반복하지 않는다.

### 실패 뒤 low-water와 정상 재상승의 차이

`실패33→WAIT→사용자가28로 정리→33으로 재충전`에서는 실제 low-water를 기록하고 다음 압력의 계획 평가를 허용한다. 이것이 예전 실패나 소진 한도를 지우는 것은 아니다. 같은 실패 목적지와 조건이 그대로인 경우에는 동일 작업을 다시 시작하지 않으며, 현재 계획과 차단 이유를 대조한다. 차단 원인과 관련된 변화가 있으면 해당 범위의 제한된 재확인 기회를 검토한다. 이 변화가 성공을 미리 보장할 필요는 없지만, 같은 문제가 확인되면 다시 대기해야 한다. 실패 범위와 재확인 제한의 구체적인 연결은 미확정 항목에서 결정한다.

따라서 low-water는 **압력 대기 해제**이고, 실패 목적지·실행 한도·제어 차단의 무조건 해제가 아니다. `STOP→28→33`은 계획 평가로 자동 실행을 되살리지 않는다. 실제 STOP 차단이 유지되면 관측만 하며 Task 시작은 0회다.

`33→준비36→종료34`는 순감소가 -1이지만 전송이 전혀 없었다는 뜻은 아니다. 반대로 진단 로그의 pairedDeltaObserved를 읽어 재실행을 허가하지 않는다. 동작 소유자의 진척 정보가 없다면 전송 기여는 UNKNOWN이며, 정해진 유한 복구 범위 밖의 연속 실행을 허용하지 않는다.

### 실패 원인과 재확인 범위

| 확인된 실패 | 다시 평가할 근거의 예 |
| --- | --- |
| 사용할 상자 부재·공간 부족 | 다른 사용 가능한 보관소가 생김, 기존 보관소의 수용 공간이 실제로 늘어남 |
| 특정 보관소 접근 실패 | 관련 접근 조건 변화, 다른 보관소가 유효한 후보가 됨 |
| 실제 정리 효과 없음 | 보관 가능한 surplus나 목적지 조건이 달라져 효과 있는 계획의 가능성이 생김 |

방어 종료·무기 교체·먹기·새 Task identity는 관계없는 보관 실패의 초기화 근거가 아니다. 실패 기록은 원인과 목적지 등 필요한 범위에 결합한다. 특정 상자 실패를 모든 상자의 영구 차단으로 확대하지 않는다. 다른 상자의 확인도 같은 압력 구간의 반복 제한 안에서 처리하며, 후보를 A↔B로 바꾸기만 해 한도를 충전하지 않는다. 관련 변화로 제한된 재확인을 허용하는 것과 이전 실패 이력을 삭제하는 것은 별개다.

## 실패·무진척·후속 실행 제한의 소유

현재 “압력 구간”은 인벤토리 공간 부족으로 시작해 관련 보관·후속 평가·안전 대기가 이어지는 범위를 뜻한다. 실패·진척·무진척과 후속 실행 제한은 기존 Runtime/PressureChain 소유 경계에서 유지한다. 독립 책임을 분리해야 할 경우에만 좁은 인스턴스 객체를 composition으로 주입한다. 개별 Task 재생성으로 기록을 잃거나 새 static/global 상태·거대한 retry manager를 만들지 않는다.

| 한도 | 요구 | 현재 결정 수준 |
| --- | --- | --- |
| 실제 실패・무진척 | 실제 보관 기회에서 확인한 사건·누적 실행량을 보존. 방어 중단 자체는 소비 0 | 원인별 판정·측정 hook·수치는 미확정 |
| 같은 압력 구간의 후속 실행 | 부분 성과가 있어도 동일 정리 과정의 연속 실행을 유한하게 제한. 방어 후 재개·Task 재등록만으로 후속 실행을 추가 소비하지 않음 | 총 root 등록2회 제안 철회. 실제 후속 단계의 경계·수치는 미확정 |
| 실패 조건 변화의 재확인 | 원인과 관련된 실제 변화에 한정된 확인 기회. 같은 조건의 반복 관측으로 재발급하지 않음 | 원인·목적지 범위와 발급·소비 경계는 미확정 |
| 누적 실제 실행 tick | 한 Task 내부의 상자/판자/원목 확보 정체도 제한. 방어 대기 시간 제외, 중단 전 실제 누적량 유지 | 유한 상한 필요, 숫자와 측정 hook은 미확정 |
| 보관소 준비/실패 목적지 | 필요 시 automatic-only 준비 허가와 실패 이유 유지 | 기존 Task 재사용·후속 단계 구분 확인 후 최소 연결 결정 |

상한은 실제 보관 진행에서 같은 실패·무진척·후속 실행을 반복하지 못하게 하는 제한이다. 시간이 지나면 다시 실행하는 타이머나 방어 양보 횟수 제한이 아니다. 등록 횟수·선점 횟수는 관측할 수 있지만 보관 실패의 대리 지표로 사용하지 않는다. 진척으로 무진척 측정을 갱신할 수 있는 경계도 실제 동작 기준으로 정의하며, 선점·계획 변경만으로는 갱신하지 않는다.

다음 항목은 한도 초기화 근거가 아니다.

- child 재생성, 다음 general 단계, Task.reset/onStart, 새 immutable plan.
- Idle, 새 명령 root, plan epoch, 로그 operation key.
- 단축바·선택 아이템·selected chain·Task identity 변경.
- 자동보관 자신이 만든 원목/판자 유입, 상자 준비, 자식 교체.
- 방어 선점·안전 회복, 무기 교체·먹기. 이 사건은 실패를 추가하지도, 이전 실제 실패를 삭제하지도 않음.

현재 fingerprint에는 userTaskRoot identity, Task 경로와 selected chain identity, 슬롯·selectedMainHand가 들어간다. fingerprint 변경은 재계획 필요성을 관측하는 자료일 수 있지만, 그 자체로 실행 예산을 충전하지 않는다. 새 계획에는 **현재 working-set**을 사용하고 이전 Task의 보호 수량을 그대로 재사용하지 않는다.

새 기회의 근거는 다음 두 경로로 나눈다.

| 경로 | 허용 근거와 제한 |
| --- | --- |
| 정상 종료 후 새로운 압력 | 유효한 정상 결과·소유 트리 cleanup과 종료 33칸 미만을 보존한 뒤, 이후 33칸 이상 관측을 그 종료 기준점에 대해 한 번 소비한다. 28칸 이하의 기존 low-water 경로도 포함한다. 개별 아이템의 외부 획득 증명을 일괄 요구하지 않으며 새 압력 구간의 유한 실행 한도를 적용한다. |
| 실패/차단의 회복 | 알려진 실패 보관소의 수용 조건 개선이나 다른 유효 후보처럼 차단 이유와 관련된 실제 변화가 필요하다. 성공을 보장하지 않아도 제한적으로 재확인할 수 있다. 단순 슬롯·Task identity·명령 변경은 허가나 새 예산이 아니다. 동일 기회나 상태 A↔B 왕복을 반복 소비하지 않는다. |

같은 실행의 준비·회복 자식이 아직 살아 있거나 그 실행 내부에서 슬롯이 바뀐 것은 정상 완료 후의 새 압력이 아니다. 자동보관 자체의 원목/판자 유입이나 상자 준비만으로 **실패 회복 허가**를 충전하지 않는다. cleanup 뒤 늦게 들어온 물품을 이전 실행에 귀속할 수 있는 실제 동작 경계는 미확정으로 남기되, 이 부가 정보가 없다는 이유로 모든 정상 재상승을 영구 차단하지 않는다. 실패 회복과 정상 종료 후 재상승의 판정을 혼용하지 않는다.

`정상 완료28→33`은 새 보관 수요다. 이전 압력 과정의 후속 정리 횟수 등을 이미 사용했어도 그 소진량만으로 새 수요를 막지 않는다. 반면 `실패→사용자 정리28→33`은 위 실패 후 low-water 계약을 따른다. 정상 새 압력에서도 현재 유효한 목적지별 실패·STOP·필수품 보호를 무조건 삭제하지 않는다.

일반 `DepositAllTask`의 `getIfNotPresent=false`는 보관 대상 아이템 추가 획득을 제어할 뿐, 상자 확보 fallback을 없애지 않는다. trusted Task의 2400/200/6000 tick 한도는 Task 인스턴스의 제한이며 새 자식을 반복 생성하는 전체 작업의 한도가 아니다. 성공적으로 준비한 상자는 다음 general 단계에서도 활용하고, 같은 준비 진입을 매 tick 새 시도로 세지 않는다.

## 같은 세션의 막힌 WAIT와 재시작

새 동작 코드에서 종료 이력이 없는 WAIT를 취급할 필요가 있다면 `legacy/unknown`으로 구분한다. 실제 없는 성공·30칸·28칸 관측을 만들지 않는다. 일반 hot reload를 전제하지 않으며, 이 경로가 실제 생성될 위치도 구현 시 확인한다.

종료 이력 없는 WAIT의 제한된 최초 평가와 이후 방어 재개는 구분한다. 최초 평가가 끝났다는 이유로 아직 실패가 확정되지 않은 보관 목적의 안전 재개까지 금지하지 않는다.

평가 순서는 다음과 같다.

1. 실행 허가, 명시적 STOP, 비활성화, 세션, 안전 상태, 수동 보관 충돌을 확인한다.
2. 종료 이력 없는 WAIT의 최초 평가 근거를 확인한다. 이미 평가해 확인된 NO_SAFE·목적지 부재 등은 결과를 유지하고 같은 입력으로 반복 평가하지 않는다.
3. 현재 inventory·working-set·정책·목적지를 읽어 평가한다.
4. READY이면서 현재 제어와 적용되는 실제 실패·무진척·후속 실행 제한이 허용할 때 실행한다. 평가 성공과 실행 승인은 별개다.
5. NO_SAFE/목적지 부재/동일 실패/조회 불가는 원인별 대기로 남긴다. 다음 tick에 같은 평가·상자 제작을 반복하지 않는다.

STOP 여부나 실행 허가가 불명확하면 자동 실행을 시작하지 않는다. 저비용 변화 관측과 이동·열기·재료 수집 같은 실행을 분리한다.

### 평가 직후 선점과 실제 실행의 구분

방어 선점은 보관 실행권을 잠시 양보하는 사건이다. 중단 전에 확정되지 않은 접근 실패를 새로 만들지 않으며, 이미 확정된 실패를 지우지도 않는다. 안전해진 뒤에는 이전 슬롯 조작·이동 명령을 그대로 이어 붙이지 않고 현재 위치·인벤토리·working-set·목적지로 계획을 검증한다. 기존 보관 목적과 그 목적에서 확인한 결과·누적량은 유지한다.

root 등록 전 또는 등록 뒤 첫 tick 전에 방어가 선점했다면 해당 중단의 실패·무진척 소비는 0이다. 등록 이후 실제 실행 tick도 0일 수 있다. 같은 목적을 재개하기 위한 재등록이나 재평가 횟수 자체는 보관 실패·후속 실행 한도가 아니다. 방어 전에 실제로 행동한 시간과 확인된 진척·실패는 기존 기록에 남긴다.

방어 종료는 중단된 실행을 재평가할 근거다. 미완료인 동일 보관 목적을 재개하며, 새 실패 복구 기회를 발급하거나 이전 기록을 초기화하지 않는다. 이미 상자 부족·접근 실패·무진척 한도가 확정됐다면 그 원인과 관련된 변화 없이 방어 종료만으로 실행하지 않는다. 반대로 실제 실패·무진척이 없는데 선점 횟수나 안전 재평가 허가가 소진됐다는 이유로 영구 대기시키지 않는다.

| 사건 | 보존할 결과와 다음 판단 |
| --- | --- |
| READY→등록 전/첫 tick 전 방어→안전 회복, 여러 번 반복 | 보관 실패 소비 0. 안전하고 STOP·수동 충돌 등이 없으면 현재 계획으로 재개 가능. 등록 횟수만으로 한도 종료하지 않음 |
| 접근 중 방어, 접근 실패는 미확정 | 중단으로 기록. 이전 실제 실행량은 보존하고 안전 회복 뒤 현재 접근 조건으로 재평가 |
| 접근 실패 확정→방어→안전 회복 | 기존 접근 실패 유지. 관련 접근 조건 변화나 다른 유효 목적지 등 제한된 재확인 근거 필요 |
| 짧은 실제 무진척 실행→방어→짧은 실제 무진척 실행 반복 | 방어 시간은 제외하되 실제 무진척 누적량은 유지. 적용 상한에 도달하면 실제 무진척 사유로 제한 |

위험이 지속되어 보관할 수 없는 동안은 안전 대기가 정상이다. 위험이 사라지고 실제 실행 근거도 유효한데 선점 횟수만으로 막히는 상태를 금지한다. 불필요한 재계획 반복은 안전 상태 변화·계획 유효성 관측 등 기존 경계에서 줄이고, 방어 재개 횟수 제한으로 해결하지 않는다.

계획 READY 판정과 실제 root 등록 사이에도 STOP·세션 변경·수동 보관·안전 선점이 발생할 수 있다. 등록 직전에 현재 제어와 기존 계획의 유효성을 다시 확인하고, 오래된 READY나 허가가 STOP을 우회하지 못하게 한다. 이 확인을 위해 부수효과가 있는 getPriority를 추가 호출하지 않는다.

현재 실행 중인 옛 JAR은 새 소스 작성만으로 바뀌지 않는다. 새 프로세스의 초기 ARMED는 **새 세션 초기화**이고, 같은 세션의 WAIT 복구 증거가 아니다. 의미 없는 trust/untrust 반복을 영구 해결책으로 삼지 않는다.

## 자동방어·STOP·수동 보관·물품 보호

**자동방어는 자동보관보다 항상 우선한다.** 기존 공격·회피·무기 선택과 먹기 등 생존 동작을 유지한다. 보관 완료를 위해 방어를 끄거나 보관 우선순위를 올리지 않는다. 이 설계로 기존 생존 체인 사이의 우선순위를 재편하지 않는다. `MobDefenseChain.getPriority()`는 동작을 수행하므로 조회 목적으로 추가 호출하지 않는다. 이미 평가된 정상 동작의 읽기 경계와 실제 tick 순서를 확인한다.

선점에서는 보관 소유 Task/입력만 정리한다. 방어가 사용하는 입력·경로를 취소하거나 방어가 선택한 무기를 중단 전 슬롯으로 되돌리지 않는다. 보관 cleanup 자체도 방어 실행을 가로막지 않도록 소유 경계를 지킨다. 안전 회복 뒤에는 현재 조건으로 재계획하며 이전 실제 실패·무진척·진척을 이어 쓴다. stopped Task를 무조건 reset해서 재사용하지 않는다.

STOP은 RUNNING뿐 아니라 ARMED/WAIT에서도 보존한다. 현재 `startTask()`는 비활성 runner를 enable할 수 있으므로 재평가가 STOP을 뒤집지 않도록 제어 원인을 전달한다. `runner.isActive()==false`만으로 정상 Idle과 명시적 STOP을 동일 취급하지 않는다. 명시적 재개와 실패 예산 초기화도 별도 판단이다.

STOP 후 재활성화는 현재 소스로 확인한 **가능 경로**이며, 이번 실행에서 실제 발생했다고 단정하지 않는다. 이 설계를 이유로 MobDefenseChain/TaskRunner 전체를 재설계하지 않는다. 자동보관 소유 경계에서 부족한 제어·선점 이유 연결만 필요한 경우 추가한다.

수동 store_home/deposit 충돌 검사와 사용자 보관 우선권, trusted 물품을 일반 상자로 강등하지 않는 정책, HARD_PROTECTED·장착/주력 도구·먹을 것·reserve·metadata·현재 작업 필수품 보호를 유지한다. 재개에서도 현재 인벤토리와 현재 작업으로 보호 대상을 확인하며 중단 전 목록만 재사용하지 않는다. 필수품 회복 뒤 deficit이 남은 결과를 성공 기반 재무장에 사용하지 않는다.

## 파일별 책임과 구현 단위

공통 기존 경로는 `runtime/chatclef_fabric_1.20.1/src/main/java/lavi/minecraft/task/container/deposit/auto/`다. 표의 신규 경로는 제안이다.

| 파일/폴더 | 역할 |
| --- | --- |
| StateMachine / State / 필요 시 Signal | 순수 상태 전이. 게임 조회·로깅·Task 생성 제외 |
| 신규 `maintenance/result/` | 불변 동작 결과와 유효성·종료 이유 |
| 기존 `maintenance/relief/` | pressure 조회 상태와 부호 있는 순변화·기존 분류 |
| 신규 `rearm/` | 결과·현재 관측·제어 상태에 따른 평가/실행 허용 판단 |
| 필요 시 `budget/` | 기존 자동보관 소유 경계에 결합된 실제 실패·무진척·후속 실행 제한. 방어 선점/재등록 횟수는 차단 한도로 사용하지 않음 |
| MaintenanceTask | 한 실행의 자식 결과·필수품·pressure 수집 및 종료 연결 |
| PressureChain | 정상 관측, 현재 계획 생성, 소유 Task 연결과 정리. 세부 정책/한도 구현은 위 타입에 위임 |
| 기존 `composition/AutoDepositRuntimePreparation.java`, `DepositAllInventoryPressureChainPreparation.java` | 인스턴스 의존성 생성·주입 |
| 필요 시 maintenance/child 및 일반 DepositAllTask의 최소 연결 | automatic-only 보관소 준비 허가. 수동 동작과 기존 탐색/제작 엔진 유지 |
| 기존 diagnostics 하위 폴더 | 결정된 동작 결과의 수동적 관측 |

기존에 같은 책임 소유자가 있으면 재사용한다. 위 폴더 표는 의무적인 새 관리 계층 목록이 아니다. 실행·대기 흐름 안에서 대기 이유와 실제 결과를 먼저 구분하고, 새 LAVI 타입에 독립 책임 둘 이상이 생기면 파일과 의미 있는 하위 폴더로 분리한다. 실패 원인마다 실행 상태를 늘리거나 upstream 클래스를 이동·분해해 해결하지 않는다.

구현 순서는 결과/조회 상태 → 순수 재무장/한도 → 실제 종료·제어/선점 연결 → 동작 독립 로그 → 회귀/빌드/런타임 검증으로 잡는다. 단계별 결과를 구분해서 기록하고, 재실행을 잠깐 무제한 허용하는 중간 구현을 완료 상태로 배포하지 않는다.

## 동작과 분리된 로그

run/session/압력 구간, 전후 상태, terminal/wait reason, 실제 start/pre-transfer/end 관측 여부, signed delta, 실행 우선권과 재실행 근거, 원인·목적지별 실패와 관련 변화, 소비·잔여 한도, 누적 실제 실행량, 선점 대기·STOP·cleanup을 기록한다. 등록/재개 관측 횟수와 실제 실패·무진척 소비를 별도로 남긴다. 없는 중간 snapshot을 새로 만들어 채우지 않는다. 미평가는 NOT_EVALUATED, 읽기 불가는 UNAVAILABLE로 구분한다.

`AutoDepositWaitOrigin`의 reason/enteredTick/evaluationSequence, emission failure, summaryAttemptLimit, 로그 operation과 출력 한도는 진단 전용이다. 이를 읽어 재무장·성공·시간 제한을 결정하지 않는다. 동작 소유자의 값이 진단으로 한 방향 전달되도록 한다. OFF/출력 예외/한도 소진에서도 Task 시작·종료·방어·STOP 동작은 같아야 한다.

## 미확정 설계 항목

| 항목 | 구현 전에 확인·기록할 내용 |
| --- | --- |
| 실제 실패・무진척・후속 실행 제한 | 실제 시도·실패 확정·후속 단계의 소유 경계와 유한 상수. root 등록 총2회 및 방어 재개 평가 횟수 소진 방식은 철회한 제안으로 유지 |
| 누적 실제 실행량 | 실제 보관 실행·진척의 측정 hook, 무진척 상한과 근거, 방어 대기 제외, 재개 때 기존 누적량 보존, 종료·정리 경계 |
| 실패 재확인 | 원인·목적지별 관련 변화와 한정된 확인 범위, 같은 기회 소비 식별, 새 후보의 유효성, 자체 물품 유입·A↔B 왕복에 의한 재충전 방지 |

| 종료 이력 없는 WAIT | 새 구현에 실제 유입 경로가 있는지와 같은 세션 복구 범위. 옛 실행 JAR hot reload 가정 금지 |

위 미확정 사항을 외부 검토문만으로 확정했다고 표시하지 않는다. 향후 구현 작업의 소스 대조와 정책 결정 결과로 문서를 갱신하며, 이번 문서화만으로 테스트나 런타임을 실행하지 않는다.
