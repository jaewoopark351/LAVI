## 3. Exact decisions

### 3.0 공통 입력·언어 범위

Feature A/B/C는 모두 실제 LAVI Chat 또는 VoiceInput-final adapter가 생성한 뒤 별도 trusted ingress coordinator가 one-shot claim으로 인수한 input event이고, 다음 typed tuple과 한국어 eligibility를 동시에 만족할 때만 새 동작을 소유한다.

| 입력 경로 | source | provider_id | event_kind | final |
|---|---|---|---|---:|
| LAVI Chat 최종 제출 | `lavi_chat_ui` | `lavi_chat_ui` | `chat_submit` | `true` |
| 마이크 최종 인식 | `voice_input_final` | `VoiceInput` | `final_transcript` | `true` |

source tuple만으로는 실제 ingress를 증명할 수 없다. 기존 H5 계약대로 `LocalChatInputEventAdapter`와 exact VoiceInput-final `ProviderBoundInputEventAdapter`는 event 생성, event ID 발급과 immutable provenance stamping만 담당한다. 두 adapter는 `TrustedUserInputIngressClaimRegistry`를 import하거나 claim 등록·handoff·consume·abandon을 직접 수행해서는 안 된다.

application wiring은 실제 local Chat UI callback과 exact VoiceInput-final provider callback entrypoint에 각각 `TrustedLocalChatInputDispatchCoordinator`와 `TrustedVoiceInputFinalEnqueueCoordinator`를 합성한다. `TrustedIngressProducerRegistrarFactory`는 그 실제 callback invocation에만 유효한 private producer-bound registrar capability와 `TrustedIngressCreationTicket`을 만들고 coordinator에만 주입한다. registry에는 caller가 임의의 `event`만 넘길 수 있는 public `register(event)`, `reopen(event)` 또는 source-string lookup API가 없다. capability/ticket은 exact adapter instance와 immutable provider policy, 현재 callback invocation, exact `LaviInputEvent` object identity, event fields와 bounded text hash/length에 묶이며 등록 성공·거절·포기 중 하나에서 한 번 소진된다. adapter, event, mapping, source 문자열, serialized token 또는 이전 callback capability만으로 claim을 재구성하거나 terminal event를 재등록할 수 없다.

registry의 initial `4096`은 영구 tombstone 수가 아니라 동시에 살아 있는 `REGISTERED`, `QUEUE_OWNED`, `DISPATCH_OWNED` claim의 상한이다. `CONSUMED`/`ABANDONED` terminal에서 live record는 즉시 제거하되 invocation-local registrar capability는 이미 소진되어 같은 event object를 되살릴 수 없다. 정상 대화가 누적돼 capacity를 소진해서는 안 되고 live claim은 자동 eviction하지 않는다. terminal에서 비워진 capacity slot은 이후의 새 trusted adapter invocation이 만든 새 event가 사용할 수 있다. 실제 concurrent-open overflow만 fail-closed한다.

ownership handoff는 다음처럼 고정한다.

```text
local Chat:
  trusted local-Chat callback invocation
    -> LocalChatInputEventAdapter creates/stamps event only
    -> TrustedLocalChatInputDispatchCoordinator: REGISTERED
    -> atomic REGISTERED -> DISPATCH_OWNED immediately before predict/dispatch handoff
    -> top-level input dispatch: DISPATCH_OWNED -> CONSUMED
    -> any failure before consume: current coordinator owner -> ABANDONED

VoiceInput final:
  trusted VoiceInput-final callback invocation
    -> ProviderBoundInputEventAdapter creates/stamps event only
    -> TrustedVoiceInputFinalEnqueueCoordinator: REGISTERED
    -> generic Input.send_output fan-out (not an ownership acknowledgement)
    -> exact claim-aware LLM queue sink atomically accepts the queue item
       and transitions REGISTERED -> QUEUE_OWNED before issuing QueueAcceptanceReceipt
    -> dequeue owner: QUEUE_OWNED -> DISPATCH_OWNED
    -> top-level input dispatch: DISPATCH_OWNED -> CONSUMED

Voice callback/fan-out/enqueue failure before QueueAcceptanceReceipt:
  TrustedVoiceInputFinalEnqueueCoordinator abandons REGISTERED,
  or the queue sink abandons QUEUE_OWNED if it acquired ownership before put failed

later fan-out listener or worker-start failure after QueueAcceptanceReceipt:
  must not revert or abandon QUEUE_OWNED; the queue remains the sole owner

queue clear/drop/shutdown:
  queue owner uses the exact queue ownership token to transition each removed
  unconsumed QUEUE_OWNED claim to ABANDONED

dispatch failure/fallthrough:
  dequeue/direct coordinator first transfers to DISPATCH_OWNED;
  top-level input dispatch consumes/removes the claim exactly once and closes
  any issued proof in finally, or abandons DISPATCH_OWNED if consume never committed
```

`QueueAcceptanceReceipt`은 exact queue entry와 queue ownership token에 묶인 non-serializable process-local 값이며 queue item 공개와 `REGISTERED -> QUEUE_OWNED`가 하나의 enqueue commit으로 성공한 뒤에만 발급한다. `queue에는 item이 보이지만 claim은 REGISTERED`인 중간 상태를 다른 thread에 노출해서는 안 된다. designated `ClaimAwareLlmInputQueueSink`가 0개 또는 2개 이상이거나, sink 호출 전 exception, enqueue 거절 또는 queue insertion failure이면 receipt가 없다. 반대로 receipt 발급 뒤의 다른 fan-out listener exception, queue UI update exception 또는 worker start exception은 이미 인수된 queue entry를 producer failure로 되돌리지 않는다. dequeue, clear/drop/shutdown은 receipt의 exact token을 제시한 queue owner만 상태를 전이할 수 있고, producer coordinator는 `QUEUE_OWNED` 이후 claim을 abandon할 수 없다. claimed Voice event를 plain `llm.receive_input` edge로 동시에 다시 enqueue하지 않으며, non-Voice/unclaimed provider input은 기존 `llm.receive_input` 경로와 결과를 유지한다.

planned ownership API의 의미는 다음으로 닫는다. `RegisteredIngressDelivery`는 event와 opaque registry/producer binding을 함께 운반하며 event만으로 재구성할 수 없다. `ClaimAwareLlmInputQueueSink.offer_registered(delivery)`는 queue insertion과 `QUEUE_OWNED` commit이 모두 성공할 때만 `QueueAcceptanceReceipt`을 반환한다. top-level dispatch의 Chat `accept_registered(delivery)`와 Voice `accept_queued(queue_delivery)`는 각각 `DISPATCH_OWNED` lease를 만들고, 그 lease의 `consume_for_eligibility()`만 source/language gate 전에 `ConsumedIngressEvidence`를 반환하며 `CONSUMED`로 전이할 수 있다. 모든 transition은 exact registry/event/current-owner token을 확인하는 CAS이고 역전이는 없다.

공통 ingress registry는 H5 feature-specific `AutoDepositTrustInputEventClaimRegistry`와 별개다. 양쪽 receipt/ticket/lease는 서로 대신 등록·검증·소비할 수 없고, 이번 wrapper/coordinator가 H5 adapter의 event 생성/stamping-only 책임을 확장하지 않는다.

gate 성공은 caller가 만든 boolean이나 source 문자열이 아니라 input-dispatch-owned `KoreanChatMicrophoneEligibilityProof`를 발급해야 한다. proof는 consumed ingress claim의 exact `event_id`, 위 canonical tuple, original text의 bounded hash/length와 발급 owner에 묶인 immutable process-local object다. 공통 `event_id`도 exact built-in `str`의 lowercase `[0-9a-f]{32}`여야 하며 누락, uppercase, 길이/문자 불일치 또는 subclass 값은 fail-closed한다. JSON/pickle/DTO 직렬화와 caller-side 재구성을 허용하지 않으며, 해당 top-level input dispatch의 `finally`에서 닫혀 이후 재사용할 수 없어야 한다. Feature A의 immediate publisher와 Feature B의 scoped translation은 proof가 열린 동안 commit되어야 한다. STOP은 열린 proof에서 §9.3의 별도 one-shot stop claim을 발급한 뒤 비동기 lifecycle을 그 claim/control identity로 이어 간다. proof 자체는 submit 또는 gameplay mutation 권한이 아니고 Feature A/B/C의 initial feature admission을 시작할 수 있다는 전제 증거일 뿐이다.

한국어 eligibility는 LLM 언어 추론을 사용하지 않는 deterministic gate다. exact built-in `str`의 NFKC 결과에 다음 Hangul 범위 중 한 글자 이상이 있어야 한다.

```text
U+1100-U+11FF  Hangul Jamo
U+3130-U+318F  Hangul Compatibility Jamo
U+A960-U+A97F  Hangul Jamo Extended-A
U+AC00-U+D7A3  Hangul Syllables
U+D7B0-U+D7FF  Hangul Jamo Extended-B
```

한국어 eligibility는 필요조건이지 Minecraft 명령이라는 충분조건이 아니다. 한국어 일상 대화는 계속 기존 LLM 경로로 가며, `마크 AI 멈춰`처럼 Hangul과 Latin token이 섞인 입력은 exact Korean command grammar가 일치할 때만 허용한다. `stop`, `get map 1`, `make a button`처럼 Hangul이 없는 입력에는 이번 feedback/alias/STOP 기능을 적용하지 않는다.

이 gate의 NFKC copy는 Hangul 존재 여부만 판정하고 원본 text를 덮어쓰지 않는다. 특히 STOP raw-safety guard에는 질문부호·인용·줄바꿈이 그대로 남은 original raw text를 전달해야 하며, language gate가 punctuation을 제거하거나 안전 검사를 선행 대체해서는 안 된다.

마이크 partial/interim, `direct_typed`, `lavi_gui_korean`, Twitch/YouTube/external chat, ScreenVision와 다른 plugin 입력은 이번 새 기능 범위 밖이다. 이 계약은 그 경로와 비한국어 입력의 기존 동작을 새로 활성화하거나 비활성화하지 않는다. 단지 Feature A/B/C가 그 입력을 소유하거나 새 Minecraft submit/publisher/control을 만들지 못하게 한다. serialized provenance, language flag, source 문자열 또는 다른 owner가 발급한 proof만으로 이 범위를 우회할 수 없다.

```text
recognized and submitted
  -> 제출 사실만 안내

recognized but rejected
  -> busy/disconnected/unsupported/unknown-item 이유 안내

unrelated ordinary conversation
  -> Minecraft가 소유하지 않고 기존 LLM 대화 경로로 전달
```

제출 직후 응답은 완료 증거가 아니다. `만들었어요`, `가져왔어요`, `멈췄어요`처럼 아직 증명되지 않은 결과를 말하지 않는다.

### 3.2 재료를 생략한 제작 요청

초기 public 기본값은 다음 네 catalog target으로 고정한다.

| 한국어 item phrase | catalog target | prefixless DSL | 계약 의미 |
|---|---|---|---|
| `다락문` | `trapdoor` | `get trapdoor 1` | 기존 Java alias가 `wooden_trapdoor`로 연결하므로 임의의 나무 다락문을 준비 |
| `지도` | `map` | `get map 1` | `Items.MAP`, 즉 빈 지도만 준비 |
| `압력판` | `wooden_pressure_plate` | `get wooden_pressure_plate 1` | matching-plank task가 선택하는 임의의 나무 압력판을 준비 |
| `발판` | `wooden_pressure_plate` | `get wooden_pressure_plate 1` | `압력판`의 사용자 표현 alias |
| `버튼` | `wooden_button` | `get wooden_button 1` | matching-plank task가 선택하는 임의의 나무 버튼을 준비 |

이 표의 `1`은 ChatClef가 보유해야 할 최소 목표 수량이다. 레시피 산출량이나 기존 인벤토리 때문에 실제 증가량이 정확히 1이라는 뜻은 아니다.

Feature B는 deterministic rule parser가 LLM fallback 없이 `GET_ITEM`을 만들고 기존 `KoreanAcquisitionVerbMatcher.classify()`가 `craft`를 반환한 제작 문장에만 적용한다. 즉 기존 `만들어줘`/`만들어 주세요`/`제작해줘`/`제작해 주세요` 계열은 허용하지만 acquire/mining verb, raw DSL, LLM-origin intent, `EQUIP_ITEM`, `DEPOSIT_ITEM`, `GIVE_ITEM`에는 이 다섯 기본값을 사용하지 않는다. parser가 기존 NFKC/공백 처리, quantity 제거, acquisition-verb 제거와 terminal particle 제거를 마친 `item_phrase`가 표의 exact key와 같아야 한다. substring match는 금지한다. exact candidate의 수량이 유효하지 않으면 `OWNED_INVALID` handled-no-submit이며 unscoped translator나 LLM으로 fall through하지 않는다.

### 3.3 정지 의미

`멈춰`는 일반 두 번째 task command가 아니라 우선순위가 높은 `STOP_AI` control이다. 의미는 Minecraft 프로세스 종료나 bridge 종료가 아니라 다음 기존 명령과 같다.

```text
ChatClef StopCommand
  -> AltoClef.stop()
  -> current/user task chain stop
  -> task runner and idle automation stop
  -> Baritone current path cancellation
  -> AltoClef-owned input override release
```

따라서 `MinecraftFabricChatClefExtension.stop()`처럼 WebSocket/plugin lifecycle을 종료하는 메서드를 AI 정지에 재사용해서는 안 된다.

신뢰된 exact 정지 발화는 tracked LAVI command 유무와 관계없이 현재 ChatClef/AltoClef 자동화를 멈추는 global emergency control이다. 추적 중인 pending/active command의 complete immutable retirement snapshot을 만들 수 있을 때만 그 exact identity를 `tracked_command` correlation으로 함께 보내 원래 command를 안전하게 `cancelled/user_stop_requested`로 retire한다. tracked command가 없거나 snapshot이 불완전하면 target 없는 `current_global_automation` profile로 보내며, Java client tick이 그 시점의 현재 automation을 기존 StopCommand로 정지한다. target fields는 실행 범위를 좁히는 권한이 아니라 original retirement correlation일 뿐이다. event claim, live session/generation, 2000 ms deadline, Python/Java의 별도 stop-control admission barrier, 기존 ordinary-owner gate와 non-replay 규칙이 늦거나 중복된 control을 제한한다. 한 번 권한 있게 실행된 StopCommand의 내부 전역 정리 의미는 변경하거나 부분 복제하지 않는다.

## 4. Current repository observations

문서 작성 시점의 source-backed 관찰은 다음과 같다.

### 4.1 응답은 생성되지만 마이크 경로에서 유실된다

- `ChatClefCommandResponseRenderer`는 제출/거절/unknown 응답을 이미 deterministic하게 만든다.
- `LLM.predict_wrapper()`는 Minecraft route response를 `yield`하고 반환하므로 로컬 Gradio Chat은 응답을 표시할 수 있다.
- `LLMInputQueueRuntime.drain_queue()`는 마이크 입력에서 반환된 generator를 순회하지만 yielded value를 전달하지 않는다.
- 일반 LLM 응답은 generation-tagged output listener 경로를 통해 Translate와 TTS로 전달된다.

즉 현재 구조는 다음처럼 비대칭이다.

```text
LAVI local Chat
  -> Minecraft response yield
  -> Chat UI can display it

VoiceInput final transcript
  -> Minecraft response yield
  -> queue drain consumes and discards it
  -> no routed output/TTS feedback
```

### 4.2 일반 제작어는 catalog에 있어도 Korean exact alias가 없다

현재 offline translation probe 결과는 다음과 같다.

```text
다락문 만들어줘  -> unknown_item_phrase
지도 만들어줘    -> unknown_item_phrase
압력판 만들어줘  -> unknown_item_phrase
발판 만들어줘    -> unknown_item_phrase
버튼 만들어줘    -> unknown_item_phrase
```

반면 `빈 지도`, `돌 압력판`, `돌 버튼` 같은 구체 표현과 `trapdoor`, `map`, `wooden_pressure_plate`, `wooden_button`, stone variant catalog token은 컴파일된다. `TaskCatalogue`는 generic wooden target을 matching-plank collector에 연결한다. 결함 위치는 새 Java recipe가 아니라 Korean generic alias 해석 경계다.

현재 `FabricChatClefCommandController.submit_korean_command()`는 `source=lavi_gui_korean` request를 만들고 `MinecraftChatClefInputRouter`를 거치지 않은 채 `MinecraftFabricChatClefExtension.handle_natural_language_command()`를 직접 호출한다. 그 경로와 Chat/마이크 router 경로는 `NaturalLanguageCommandCoordinator`와 `KoreanItemPhraseResolver`의 공용 `korean_item_aliases.json`을 공유하며, public `get` registry도 기존 계약상 `lavi_gui_korean`과 `direct_typed`를 허용한다. 따라서 다섯 mapping을 전역 `CURATED_ALIASES`/generated JSON에 추가하면 §3.0 밖 GUI에도 새 동작이 누출된다. Feature B는 공용 artifact가 아니라 proof-gated request-local alias profile로 격리해야 하며, 기존 `get`의 allowed source 목록 전체를 좁혀서 해결해서는 안 된다.

### 4.3 현재 typed tuple만으로는 실제 ingress를 증명하지 못한다

`LaviInputEvent`는 공개 frozen dataclass이고 `LaviInputEventNormalizer.normalize()`는 전달받은 instance를 그대로 반환한다. 따라서 현재 구조에서 caller가 canonical tuple과 32자 event ID를 복사해 새 instance를 만들면 field 비교만으로 실제 Chat/Voice adapter 출력과 구분할 수 없다. §3.0의 factory-issued producer capability와 coordinator-owned ingress claim은 adapter 책임을 늘리지 않으면서 이 source-backed 간극을 닫기 위한 미래 구현 계약이다. 단순 tuple validation이나 공개 `register(event)` 호출을 origin authentication이라고 기록해서는 안 된다.

### 4.4 STOP은 번역 가능하지만 실행 중에는 도달할 수 없다

현재 rule parser는 다음 exact phrase를 `STOP`으로 만들고 compiler는 prefix 없는 `stop`을 생성한다.

```text
멈춰
멈춰줘
중지
정지
스톱
그만
```

그러나 registry의 STOP row는 public/Python admission이 닫혀 있고 입력 source도 제한되어 있다. 그 플래그만 열어도 요구사항은 충족되지 않는다.

```text
Python generic precheck
  -> active_request_id가 있으면 busy 거절

Python transport admission
  -> active command가 있으면 두 번째 command 거절

Java FabricChatClefCommandQueue
  -> pending 또는 active가 있으면 offer 거절

Java FabricChatClefCommandDispatcher
  -> active가 있으면 새 command dispatch 전에 return
```

따라서 가장 정지가 필요한 `작업 실행 중`에는 ordinary `command_request(stop)`가 실행되지 않는다. 또한 기존 command result handler에 stop을 억지로 끼우면 원래 active command와 stop control의 identity/retirement가 충돌한다.

## 5. Target end-to-end flow

```text
actual trusted Chat/Voice callback entrypoint
  -> LocalChatInputEventAdapter OR exact VoiceInput-final ProviderBoundInputEventAdapter
     creates/stamps the event only
  -> factory-bound coordinator registers the exact object in
     TrustedUserInputIngressClaimRegistry with a one-shot producer capability
  -> Chat: REGISTERED -> DISPATCH_OWNED
     Voice: REGISTERED -> QUEUE_OWNED -> DISPATCH_OWNED
  -> top-level input dispatch atomically transitions the matching claim
     DISPATCH_OWNED -> CONSUMED once
  -> exact common source tuple validation
  -> deterministic Korean eligibility gate
     | not eligible -> no new Feature A/B/C ownership; preserve existing path
     | eligible -> issue top-level-input-dispatch-scoped opaque eligibility proof
  -> STOP_AI tri-state whole-utterance classifier (highest Minecraft route priority)
     | VALID_EXACT_STOP
     -> one-shot stop claim
     -> dedicated control admission over the existing v1 command envelope
     -> Fabric WebSocket validates/enqueues only
     -> END_CLIENT_TICK executes existing StopCommand exactly once
     -> stop-profile command_result
        + original command cancelled result when a Java ordinary context exists
     -> one truthful immediate response and one deduplicated terminal response
     |
     | GUARDED_STOP_LIKE_REJECTION
     -> handled-no-submit response
     -> ordinary STOP submit 0, LLM STOP promotion 0
     |
     | UNRELATED
     -> existing Korean Minecraft intent gate/parser
     -> existing specific item aliases keep their current behavior and precedence
     -> only an exact five-phrase generic candidate enters
        generic_crafting_defaults_v1 feature admission
     -> coordinator validates the same live eligibility proof
     -> request-local alias overlay; no global resolver/repository mutation
     -> existing prefixless get compiler
     -> existing ordinary single-active admission and command_request
     -> one truthful immediate response

Response text
  -> local Chat yield when the source is Chat
  -> LLM-owned routed external-response publisher
  -> existing output envelope/generation semantics
  -> Translate -> TTS when enabled
```

Common source/language admission must run before Feature A/B/C ownership. Every initial feature activation revalidates the live proof rather than trusting copied provenance; later stop terminal delivery relies on the already committed stop claim/control identity, not on an expired common proof. An input that fails trusted ingress, exact tuple or Korean eligibility never enters the new STOP classifier and receives no new Feature A rejection; its pre-existing route/fallthrough remains unchanged. After common admission, STOP classification runs before generic busy rejection and before LLM intent fallback. A stop-like admitted Korean input rejected by the raw guard or STOP-specific claim/admission must not fall through to the shared normalizer, legacy STOP parser, or LLM extractor. Within this admitted Chat/final-microphone dispatch, the ordinary parser/compiler may not submit `stop`; only a valid control claim may do so. This does not newly disable or enable legacy GUI/direct paths outside §3.0. STOP bypasses ordinary task-command busy/reconciliation admission only through its own control lane. It does not bypass Korean eligibility, typed-source validation, live session/generation checks, one-shot deduplication, or capability negotiation. The existing direct GUI natural-language handler never receives the proof and therefore cannot activate Feature B.

이번 범위에는 응답 전달, item alias, stop intent, stop transport, client-tick mutation과 terminal classification이라는 서로 다른 책임이 있다. 미래 구현은 이를 한 파일이나 기존 facade에 몰아넣지 않고 아래처럼 분리한다.

`MinecraftChatClefInputRouter`는 facade와 순서 조정만 유지한다. exact stop 판정, alias table, proof registry 세부 구현, response delivery 또는 transport ownership을 직접 구현하는 새 다중책임 클래스가 되어서는 안 된다.

### 6.2 Java/LAVI-owned packages

Java 변경이 필요한 stop slice는 다음 LAVI-owned namespace 아래에서만 folderized한다.

```text

  dispatch
```

각 type은 request DTO, validator, bounded queue, tick dispatcher, result factory/sender 중 하나의 책임만 가진다. 기존 `FabricChatClefCommandQueue`의 single-active invariant를 일반화하거나 두 번째 일반 command를 허용하지 않는다.

다음 upstream-derived source는 이동, 분할, 이름 변경 또는 내부 정리 대상으로 삼지 않는다.

```text

adris.altoclef.AltoClef
adris.altoclef.tasksystem.*
adris.altoclef.commandsystem.CommandExecutor
```

필요한 연결은 LAVI-owned stop dispatcher가 기존 registered `stop` command를 실행하는 composition으로 제한한다.

### 6.3 Backend separation

```text
LAVI orchestration
  -> existing backend-neutral command request/result DTO and v1 envelope
  -> Fabric stop control adapter
  -> Fabric mod client-tick dispatcher
  -> ChatClef StopCommand
```

Forge/MineMind 디렉터리, enum value, adapter, test, config, GUI placeholder는 만들지 않는다. 이번 stop slice는 `CommandRequestDTO.metadata`와 `CommandResultDTO.data`의 기존 확장 지점을 사용하므로 common message enum, 새 DTO, 새 top-level schema union 또는 protocol version을 추가하지 않는다. socket, retry, queue, session implementation은 계속 Fabric 계층에만 둔다.

## 7. Command feedback contract

### 7.1 Ownership rule

§3.0을 통과한 handled Korean command의 응답 text는 Minecraft response renderer가 결정하고, 전달은 LLM-owned routed-response publisher가 담당한다. source/language gate를 통과하지 않은 입력에는 이 publisher를 새로 호출하지 않는다.

권장 API 의미는 다음과 같다. 이름은 구현 시 기존 naming convention에 맞출 수 있지만 책임은 바꾸지 않는다.

```text
emit_external_response(
    text,
    source="minecraft_chatclef",
    send_output=true,
    send_full_output=false,
    remember_history=false
)
```

이 API는 다음을 보장해야 한다.

- 선택된 LLM provider를 호출하지 않는다.
- `LLM.receive_input()`으로 다시 넣지 않아 command가 재귀 실행되지 않는다.
- 일반 사용자/assistant 대화 history 또는 memory에 자동 저장하지 않는다.
- LLM owner가 새 response generation을 할당하고 기존 stale-output 규칙을 유지한다. caller가 임의 generation을 만들거나 오래된 generation을 재사용하지 않는다.
- output listener 하나의 실패가 command 제출 결과나 retry 정책을 바꾸지 않는다.
- 같은 route decision과 sink에 두 번 발행하지 않는다.

### 7.2 Source별 delivery

| 입력 source/language | Chat UI | output listener/Translate/TTS | 비고 |
|---|---:|---:|---|
| eligible Korean `lavi_chat_ui` | yield 1회 | publish 1회 | 동일 응답의 서로 다른 sink이며 각 sink에서 중복 금지 |
| eligible Korean `voice_input_final` | Gradio yield에 의존하지 않음 | publish 1회 | queue drain이 값을 버려도 음성 응답 유지 |
| non-Korean 또는 scope 밖 source | 기존 동작 | 기존 동작 | 새 Minecraft publisher/submit/control 호출 금지 |
| unrelated/unhandled input | 기존 동작 | 기존 동작 | Minecraft publisher 호출 금지 |

TTS가 disabled이거나 listener가 없는 환경에서도 route decision과 Chat text는 유효해야 한다. Minecraft transport가 TTS component를 직접 참조해서는 안 된다.

### 7.3 Response truth table

| 시점/결과 | 예시 문구 | 금지 문구 |
|---|---|---|
| 일반 command transport 제출 수락 | `[Minecraft] 다락문 1개를 준비하도록 명령했어요.` | `다락문을 만들었어요.` |
| busy | `[Minecraft] 다른 마인크래프트 명령을 실행 중이라 지금은 새 명령을 보낼 수 없어요.` | 새 command 자동 queue/retry |
| disconnected | `[Minecraft] 마인크래프트 연결이 끊겨 있어 명령을 보내지 못했어요.` | `보냈어요.` |
| command-shaped unknown item | `[Minecraft] 어떤 아이템을 준비할지 이해하지 못했어요.` | 일반 LLM이 임의 DSL을 만들어 자동 제출 |
| ambiguous/unsupported | 기존 typed reason에 맞춘 deterministic 거절 | 성공 추정 |
| terminal unknown | `[Minecraft] 실행 결과를 확인하지 못했어요. 자동으로 다시 보내지 않아요.` | 자동 재전송 |

`다락문을 준비하도록 명령했어요`는 ChatClef `get` 획득 요청을 설명한다. ChatClef가 실제로 제작, 채집 또는 기존 보유분 사용 중 어느 경로를 선택했는지 제출 시점에는 단정하지 않는다.

### 7.4 Handled boundary

§3.0의 source/language gate 통과만으로도 Minecraft가 입력을 소유해서는 안 된다. 또한 `만들어줘`, `제작해줘` 같은 acquisition verb 하나만으로 소유해서는 안 된다. `보고서 만들어줘`, `일정 만들어줘` 같은 일반 LLM 요청을 가로채기 때문이다.

미래 구현에는 resolver/compiler의 문자열 reason을 사후 추정하는 대신 `OWNED_VALID`, `OWNED_INVALID`, `UNRELATED`를 반환하는 좁은 typed item-command ownership classifier를 둔다. 이 classifier만 최종 ownership result를 만들며, generic alias package가 반환하는 craft-only profile membership/candidate와 activation-admission 결과를 입력으로 소비한다. alias package 자체는 `OWNED_*`를 최종 판정하지 않는다. scoped mapping 추가만으로 command-shaped rejection 경계를 구현했다고 간주하지 않는다.

deterministic Minecraft 거절은 다음 중 하나가 추가로 증명될 때만 반환한다.

- `마크`, `마인크래프트`, exact trusted `@` form 같은 명시적 Minecraft 표지가 있다.
- item resolver가 catalog/alias family를 식별했지만 material, quantity 또는 command policy에서 fail-closed했다.
- exact public Minecraft command grammar가 intent를 소유했지만 필수 slot만 잘못되었다.

acquisition verb 외에 item-candidate 근거가 전혀 없는 unknown phrase는 기존 LLM 경로로 fall through한다.

반대로 다음처럼 Minecraft 명령이라고 확정할 수 없는 일상 대화는 계속 LLM으로 fall through한다.

```text
이 경험이 성공의 발판이 되었어
웹 버튼 디자인은 어떤 게 좋아?
게임 지도에 대해 설명해줘
보고서 만들어줘
일정 만들어줘
```

## 8. Generic crafting target contract

### 8.1 Source of truth

미래 구현에서 다섯 mapping의 source of truth는 공용 generator/JSON이 아니라 `plugins/Minecraft/fabric/chatclef/input/aliases/generic_crafting_defaults/` 아래의 immutable scoped profile 하나로 둔다.

| policy_id | phrase_rule_id | exact Korean item phrase | canonical target |
|---|---|---|---|
| `generic_crafting_defaults_v1` | `generic_trapdoor` | `다락문` | `trapdoor` |
| `generic_crafting_defaults_v1` | `generic_empty_map` | `지도` | `map` |
| `generic_crafting_defaults_v1` | `generic_wooden_pressure_plate` | `압력판` | `wooden_pressure_plate` |
| `generic_crafting_defaults_v1` | `generic_foot_plate` | `발판` | `wooden_pressure_plate` |
| `generic_crafting_defaults_v1` | `generic_wooden_button` | `버튼` | `wooden_button` |

이 다섯 mapping은 `plugins/Minecraft/tools/generate_chatclef_korean_item_artifacts.py`의 전역 `CURATED_ALIASES`와 `plugins/Minecraft/fabric/chatclef/intent/resources/korean_item_aliases.json`에 추가하지 않는다. 기존 global alias와 구체 item 표현의 동작은 그대로 둔다.

Feature B의 canonical activation 순서는 다음과 같다.

```text
MinecraftChatClefInputRouter
  -> §3.0 exact tuple + Korean eligibility proof
  -> Feature-B quantity-shape guard: zero or one supported quantity token only
  -> deterministic rule parser: intent=GET_ITEM and verb_class=craft
  -> exact normalized parser-derived item_phrase ownership classification
  -> GenericCraftingDefaultsAdmission(policy_id=generic_crafting_defaults_v1)
     -> issue immutable GenericCraftingDefaultsActivationReceipt
        with registry state ISSUED_UNBOUND
  -> NaturalLanguageCommandCoordinator scoped translation seam
     -> same-owner live proof + activation revalidation
     -> intent-layer-neutral one-request resolver overlay
     -> existing compiler; no command submission/admission yet
  -> reconstruct and validate ChatClefTranslationResultDTO
  -> registry CAS binds the immutable authorization projection below
     ISSUED_UNBOUND -> TRANSLATION_BOUND
  -> ordinary submission precheck
  -> scoped submit revalidates proof/event/request/translation projection
     -> existing get registry admission inspect/commit
     -> TRANSLATION_BOUND -> SPENT CAS immediately before command_submitter
     -> only the CAS winner invokes the possibly-effectful submit exactly once
```

`GenericCraftingDefaultsActivationReceipt`은 common proof owner/event/full tuple, raw 및 translation-input text binding, policy/rule ID, expected `GET_ITEM`, canonical target과 quantity에 묶인 immutable non-serializable object다. text binding은 현재 source 동작대로 세 값을 분리한다.

```text
raw_event_text = exact built-in event.text, unchanged
translation_input_text = event.text.strip()
expected_intent_original_text = KoreanTextNormalizer.normalize(
    translation_input_text,
    lowercase_english=false,
)
```

여기서 기존 `KoreanTextNormalizer`는 NFKC, `[,.!?，。！？]+`를 공백으로 치환, `\s+`를 U+0020 한 칸으로 접기와 양 끝 trim을 순서대로 수행한다. `lowercase_english=false`이므로 `expected_intent_original_text`의 Latin case는 보존한다. item matching에 쓰는 기존 parser `normalized` 값은 같은 normalizer의 기본 `lowercase_english=true` 결과다. scoped profile은 독립 normalizer를 만들거나 이 순서를 생략하지 않고, receipt는 raw text와 translation-input text를 각각 묶는다. 아직 존재하지 않는 translation 결과를 receipt에 사후 기록하지 않는다. 같은 owner의 registry record만 scoped translation validation 뒤 다음 authorization-relevant field의 immutable exact-value projection을 `ISSUED_UNBOUND -> TRANSLATION_BOUND` CAS로 한 번 결합한다. JSON 직렬화나 구현별 문자열 digest를 권위로 사용하지 않는다.

```text
binding_version=generic_crafting_defaults_translation_v1
status=validated
executable=true
command=get <canonical_target> <quantity>
intent_type=get_item
intent_source=rule
intent_language=ko
intent_original_text=<exact expected_intent_original_text above>
item_phrase=<exact scoped-profile Korean key>
quantity=<exact validated int>
resolved_target=<canonical_target>
all non-GET intent slots empty
```

binding owner는 `ChatClefTranslationResultDTO.from_mapping()`과 기존 validator를 통과한 결과에서 이 projection을 새 immutable value로 복사한다. `data`, human-readable `message` 또는 caller object identity는 실행 권위가 아니다. scoped submit은 같은 request/translation에서 projection을 다시 만들어 registry-held value와 exact 비교하고, 기존 `get` registry admission과 request binding이 모두 성공한 뒤 `TRANSLATION_BOUND -> SPENT` CAS를 effectful `command_submitter` 호출 직전에 수행한다. CAS winner만 submitter를 한 번 호출한다. SPENT와 submitter invocation 사이에서 process가 실패하면 안전하게 미제출로 남더라도 receipt를 되살리거나 자동 재시도하지 않는다.

`GenericCraftingDefaultsRouteOwner`가 admission issue부터 translation, DTO validation, projection binding, precheck와 submit commit까지 하나의 `try/finally`로 소유한다. effectful submitter 호출 전에 발생한 translation/DTO/projection/scoped-seam/precheck/get-admission/request-binding failure, mismatch, exception 또는 no-submit 종료에서만 `finally`가 남아 있는 `ISSUED_UNBOUND`/`TRANSLATION_BOUND` record를 `ABANDONED` terminal로 만든다. CAS가 `SPENT`에 성공한 뒤 submitter가 returned rejection, exception 또는 unknown을 내더라도 record는 SPENT로 유지하고 `ABANDONED`로 되돌리지 않으며 재발급·재제출하지 않는다. 같은 common proof/event/policy에는 activation을 최대 한 번만 발급하며 SPENT/ABANDONED record는 top-level input-dispatch 종료까지 재발급 방지 tombstone으로 유지한 뒤 proof와 함께 제거한다. registry initial capacity는 concurrent live dispatch `4096`, 자동 eviction 없음, overflow fail-closed다. 순차 요청의 terminal record가 누적되거나 process restart 전까지 capacity를 영구 소진해서는 안 된다.

이 receipt/registry는 H5의 기존 `route_claim`과 다른 named parameter/registry를 사용하며 서로 대신 소비할 수 없다. coordinator는 profile activation과 submit 직전에 proof의 owner, event identity, text binding과 open top-level input-dispatch lifetime을 다시 확인한다. missing/unbound/mismatched/spent/abandoned/forged/serialized receipt, failed projection bind 또는 scoped seam unavailable은 effectful submit 전 `OWNED_INVALID` handled-no-submit이고 unscoped translator나 LLM으로 downgrade하지 않는다.

overlay는 한 translation 호출의 local decorator/value이고 공용 `KoreanItemPhraseResolver`, `ChatClefKoreanAliasRepository`, singleton, cache 또는 generated artifact를 mutate하거나 잠시 교체하지 않는다. exact profile key만 resolve하고 그 밖의 phrase는 기존 resolver에 그대로 delegate한다. normalized exact key가 기존 global alias와 충돌하면 우선순위를 추정하지 않고 fail-closed한다. 기존 `handle_natural_language_command()`를 직접 사용하는 `lavi_gui_korean` 경로와 `direct_typed` 경로에는 proof/profile/activation이 전달되지 않으므로 같은 문구로 새 Feature B submit/feedback이 0회다. 기존 public `get`의 allowed source 목록은 좁히지 않는다.

### 8.2 Why deterministic defaults

현재 Python translation 단계에는 live inventory, 주변 block, recipe feasibility에 대한 권위 있는 snapshot이 없다. 따라서 `나무든 돌이든 지금 가능한 것`을 번역기가 동적으로 고르는 기능으로 구현하지 않는다.

또한 ChatClef bracket target은 OR fallback이 아니다. 다음 형태는 나무 또는 돌 하나를 뜻하지 않으므로 금지한다.

```text
get [wooden_pressure_plate, stone_pressure_plate] 1
get [wooden_button, stone_button] 1
```

실패 후 다른 target을 자동 제출하는 fallback도 금지한다. 첫 요청이 실제로 일부 진행됐는지 알 수 없는 상태에서 재제출하면 중복 획득과 active ownership 충돌을 만들 수 있다.

`TaskCatalogue`는 `wooden_pressure_plate`와 `wooden_button`을 각각 `CollectWoodenPressurePlateTask`와 `CollectWoodenButtonTask`에 직접 등록하고, 두 task는 matching planks recipe를 사용한다. 반면 stone 기본값은 cobblestone 제련과 furnace/fuel 경로를 요구할 수 있다. 따라서 초기 결정값은 source-backed generic wooden target으로 고정한다. 이는 live feasibility 판단이 아니라 유효한 한 family를 정한 deterministic default다. 특정 `돌 버튼` 또는 `참나무 버튼`처럼 재료가 지정된 표현은 기존 exact target을 유지한다.

### 8.3 Exact phrase precedence

구체 표현이 generic alias보다 먼저 exact-match되어야 한다.

| 입력 | 유지해야 할 target |
|---|---|
| `철 다락문 만들어줘` | `iron_trapdoor` |
| `참나무 다락문 만들어줘` | `oak_trapdoor` |
| `빈 지도 만들어줘` | `map` |
| `지도 제작대 만들어줘` | `cartography_table` |
| `돌 압력판 만들어줘` | `stone_pressure_plate` |
| `참나무 압력판 만들어줘` | `oak_pressure_plate` |
| `돌 버튼 만들어줘` | `stone_button` |
| `참나무 버튼 만들어줘` | `oak_button` |

다음 표현은 generic alias로 축약하지 않는다.

```text
채워진 지도 만들어줘
탐험 지도 만들어줘
웹 버튼 만들어줘
성공의 발판 만들어줘
```

특히 `지도`는 `map`으로만 연결한다. `filled_map`이나 탐험 지도 성공을 추정하지 않는다.

### 8.4 Quantity

기존 quantity parser의 값 해석과 numeric constraint는 그대로 사용하되, 현재 parser가 여러 수량 표현 중 첫 값을 선택하면서 둘 이상을 제거하는 동작을 Feature B 권위로 사용하지 않는다. scoped alias package의 side-effect-free quantity-shape guard가 parser 호출 전에 위 `translation_input_text`에 기존 `KoreanTextNormalizer.normalize(..., lowercase_english=true)`를 적용한 exact parser-normalized 값에서 다음 closed lexical set의 non-overlapping quantity token 수를 센다.

```text
digit token:
  `(?<![A-Za-z0-9_])` left boundary
  + optional ASCII sign
  + one-or-more ASCII digits `[0-9]`
  + optional normalized whitespace
  + required `개` or `만큼`

Korean-number token:
  exact `하나|한|둘|두|셋|세|넷|네` + optional `개` or `만큼`
  bounded so it is not a substring of another Hangul word
```

```text
다락문 두 개 만들어줘 -> get trapdoor 2
지도 3개 만들어줘     -> get map 3
발판 4개 만들어줘     -> get wooden_pressure_plate 4
버튼 5개 만들어줘     -> get wooden_button 5
```

NFKC 뒤 ASCII가 되는 fullwidth sign/digit은 위 ASCII token으로 처리한다. 반면 Arabic-Indic, Extended Arabic-Indic, Devanagari 등 NFKC 뒤에도 ASCII `[0-9]`가 아닌 Unicode decimal digit(`Nd`)이 exact generic candidate에 하나라도 있으면, 현재 parser의 Python `\d`가 읽을 수 있더라도 `OWNED_INVALID` handled-no-submit으로 닫고 zero-token/default-1 경로에 넣지 않는다.

지원 quantity token이 없을 때만 1을 사용하고 정확히 하나면 기존 parser와 numeric constraint 결과를 사용한다. 둘 이상이거나 digit/Korean-number token이 섞여 있으면 `OWNED_INVALID` handled-no-submit이며 첫 값 선택, LLM fallback 또는 재제출을 금지한다. 현재 parser가 지원하지 않는 수량 표현은 generic item substring만으로 profile candidate로 승격하지 않으며, 별도의 Minecraft ownership 근거가 없으면 기존 경로를 유지한다. 따라서 현재 parser가 모든 모호한 한국어 수량을 이미 거절한다고 주장하지 않는다.

## 9. STOP input and safety contract

### 9.1 Rule-only, whole-utterance grammar

STOP classifier는 §3.0의 trusted ingress, exact tuple과 Korean eligibility proof가 모두 열린 뒤에만 호출한다. 그 안에서는 공용 punctuation normalization 전에 raw-text safety guard를 먼저 통과해야 한다. 현재 `KoreanTextNormalizer`는 `?`와 `？`를 제거하므로 이 순서를 지키지 않으면 `멈춰?`가 명령 `멈춰`로 승격될 수 있다.

```text
raw typed text
  -> trim leading/trailing Unicode White_Space only
  -> reject remaining control/format/line-separator characters
  -> reject question marks, quotation context, and multi-command delimiters
  -> validate and detach zero or one directly-adjacent terminal `.`, `。`, `!`, or `！`
  -> NFKC and bounded ASCII-space normalization of the suffix-free body
  -> English letters lowercased
  -> VALID_EXACT_STOP | GUARDED_STOP_LIKE_REJECTION | UNRELATED
```

따라서 question mark가 들어간 raw text는 normalization 결과와 무관하게 STOP이 아니다. raw guard는 최소 `?`, `？`, `"`, `'`, `“`, `”`, `‘`, `’`, `「`, `」`, `『`, `』`, `;`, `；`를 검사한다. 양 끝 trim에 허용하는 집합은 Python `str.isspace()`가 아니라 다음 exact code point set이다: `U+0009-U+000D`, `U+0020`, `U+0085`, `U+00A0`, `U+1680`, `U+2000-U+200A`, `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`. trim 뒤 남은 `Cc`, `Cf`, `Zl`, `Zp`, tab, CR/LF, non-ASCII space는 거절하고 token 사이의 연속 U+0020 SPACE만 하나로 접는다. Python `str.isspace()`가 true로 보는 `U+001C-U+001F`는 이 trim 집합에 없으므로 양 끝에 있어도 `Cc`로 거절한다.

control/quotation/delimiter guard를 통과한 trimmed raw text의 마지막 code point가 `.`, `。`, `!`, `！` 중 하나면 그 한 code point를 `terminal_suffix`로 떼고, 바로 앞 문자가 U+0020 또는 다른 whitespace가 아닌 경우에만 허용한다. suffix-free body 안에 같은 네 terminal punctuation이 하나라도 더 있으면 반복·혼합·내부 punctuation으로 거절한다. `terminal_suffix`는 audit용 enum일 뿐 canonical phrase에 포함하지 않는다. 그 body만 NFKC/ASCII-space normalization과 English lowercase를 거친 뒤 아래 bare 10개 phrase와 exact 비교한다. 따라서 `멈춰!`와 `멈춰。`는 `멈춰`로 비교되지만 `멈춰!!`, `멈춰.!`, `멈춰 !`와 `멈춰. 지금`은 거절된다. NFKC는 이 raw guard와 suffix 분리를 통과한 뒤에만 수행한다. 인용 부호 안의 stop 표현, command separator와 그 밖의 내부 punctuation은 STOP이 아니다. 공용 normalizer 결과를 근거 없이 그대로 신뢰하지 않는다.

초기 허용 집합은 안전 guard 이후 canonical 전체 발화가 다음 중 하나와 정확히 같은 경우로 고정한다. 영문 `AI`는 공용 규칙에 따라 canonical token에서 `ai`가 된다.

```text
멈춰
멈춰줘
중지
정지
스톱
그만
마크 ai 멈춰
마크 ai 멈춰줘
마인크래프트 ai 멈춰
마인크래프트 ai 멈춰줘
```

마지막 네 개는 이번 사용자 표현을 위한 explicit alias다. substring 검색으로 처리하지 않는다. STOP은 zero-slot이며 LLM intent extractor가 생성하거나 보완할 수 없다.

다음 입력은 중단 권한이 없다.

```text
멈추지 마
왜 멈췄어?
멈춰?
마크 AI 멈춰?
"멈춰"라는 말을 번역해줘
“멈춰?”
다이아를 캐고 멈춰
멈춰 그리고 지도 만들어줘
그만큼 만들어줘
만약 멈춰야 한다면 알려줘
```

복합 command 분해, 부정문 판별 추론 또는 질문문을 STOP으로 승격하는 LLM fallback을 두지 않는다. 분류 결과는 다음처럼 소비한다.

```text
VALID_EXACT_STOP:
  trusted provenance/claim 검증으로 계속 진행

GUARDED_STOP_LIKE_REJECTION:
  common-admitted input이 forbidden punctuation/raw safety 때문에 거절됐고,
  shared legacy parser가 STOP으로 축약할 수 있는 stop-like 입력
  -> Minecraft handled-no-submit으로 종료

UNRELATED:
  legacy parser/LLM 대화 경로로 전달 가능
  단, 그 하위 경로가 만든 STOP intent/DSL은 valid claim 없이는 제출 금지
```

따라서 `멈춰?`는 공용 normalizer가 물음표를 지운 뒤 ordinary `stop`으로 되살아날 수 없다.

trusted ingress, exact tuple 또는 Korean eligibility를 통과하지 못한 stop-like text는 위 tri-state classifier의 입력이 아니다. 그 경우 Feature A/C가 handled-no-submit이나 새 거절 문구를 만들지 않고 기존 경로를 그대로 보존한다. 반대로 common proof가 이미 열린 뒤 raw guard, STOP-specific receipt, session/capability 또는 one-shot admission이 실패한 경우에는 해당 admitted user request를 안전한 handled-no-submit으로 끝낼 수 있다.

### 9.2 Trusted provenance

STOP을 제출할 수 있는 입력은 §3.0의 Korean eligibility를 통과한 typed event의 다음 tuple로 제한한다.

| source | provider_id | event_kind | final |
|---|---|---|---:|
| `lavi_chat_ui` | `lavi_chat_ui` | `chat_submit` | `true` |
| `voice_input_final` | `VoiceInput` | `final_transcript` | `true` |

이번 public enablement 범위는 위 두 tuple의 한국어 입력뿐이다. 현재 registry에 남아 있는 `direct_typed` STOP source는 별도의 정확한 adapter/provenance 계약과 테스트가 정의되기 전에는 이 public 경로에 합치지 않는다. 순수 영문 `stop` 또는 `stop ai`는 이 control claim을 만들 수 없다.

허용하지 않는 예시는 다음과 같다.

- raw string 또는 `untrusted_legacy`
- microphone partial/interim transcript
- Twitch/YouTube/external chat
- ScreenVision observation
- StarCraft 등 다른 plugin input
- source 문자열만 위조한 mapping
- 정확한 lowercase `[0-9a-f]{32}`가 아닌 `event_id`
- 이미 사용된 동일 `event_id`

위 목록의 입력은 common proof를 얻지 못하므로 새 STOP classifier/control/publisher가 모두 0회이고 기존 입력 경로를 그대로 따른다. common proof가 열린 뒤 STOP-specific receipt 또는 control admission이 실패한 경우에만 `handled-no-submit`과 안전한 거절 응답을 만든다.

### 9.3 One-shot claim

STOP 전용 registry가 발급하는 router-owned opaque receipt는 다음 identity에 묶는다.

```text
event_id
source
provider_id
event_kind
final
normalized_stop_phrase
```

`event_id`는 built-in `str`의 정확한 lowercase `[0-9a-f]{32}`만 허용한다. H5 input-event claim 패턴과 같은 방식으로 receipt는 registry token, nonce와 object identity에 묶인 process-local capability이며 JSON/pickle/DTO 직렬화를 명시적으로 거절한다. wire에 `claim_id` 또는 receipt를 넣지 않는다. request factory는 같은 STOP registry가 발급한 유효 receipt를 원자적으로 spend한 뒤 canonical `metadata.input_event.event_id`를 audit correlation으로 복사할 수 있을 뿐이다.

receipt는 valid phrase, provenance와 event identity가 모두 검증된 뒤에만 발급된다. 발급된 claim은 §10.2의 lock-protected admission commit이 제출 또는 local rejection을 확정할 때 영구 소비되고 되돌아오지 않는다. 연결 끊김이나 capability 부족으로 send 전에 거절되거나, send 실패/unknown이 발생해도 claim을 되살리지 않는다. duplicate/concurrent claim은 정확히 한 winner만 가질 수 있다. forged/spent/mismatched receipt, 다른 registry receipt와 capacity exhaustion은 socket send 0회, engine mutation 0회다. registry capacity는 초기 `4096`으로 고정하고 자동 eviction/reuse하지 않으며, overflow는 fail-closed한다. registry instance는 input router object graph가 소유하고 정상 shutdown/test fixture reset에서만 폐기한다.

## 10. Dedicated stop control over the existing v1 wire

### 10.1 Why the lane is separate but the envelope is reused

ordinary `command_request(stop)`를 기존 command queue의 busy 예외로 바로 통과시키는 방식은 사용하지 않는다.

- 원래 pending/active command와 stop이 하나의 owner 자리를 경쟁한다.
- stop result가 원래 request를 잘못 clear할 수 있다.
- Java dispatcher의 active early-return과 충돌한다.
- 기존 single-active invariant를 약화시켜 다른 두 번째 command까지 통과할 위험이 있다.

그러나 새 top-level wire type도 필요하지 않다. 현재 v1 `CommandRequestDTO.metadata`와 `CommandResultDTO.data`는 명시적인 확장 지점이다. stop은 기존 envelope를 사용하되 typed discriminator로 별도 내부 lane에 demux한다.

```text
handshake.payload.capabilities.chatclef_stop_control_v1=true
request envelope type: command_request
request command: stop
request metadata.request_kind: stop_control_v1
request metadata.operation: stop_ai

result envelope type: command_result
result data.request_kind: stop_control_v1
result data.operation: stop_ai
```

Java request demux는 partial discriminator를 ordinary lane으로 되돌리지 않는다. 다음 중 하나면 stop-control candidate lane이 그 envelope를 독점한다.

```text
metadata.request_kind == stop_control_v1
OR metadata.operation == stop_ai
OR command == stop AND
   (metadata에 request_kind key가 존재 OR metadata에 operation key가 존재)
```

candidate lane의 validation/admission precedence는 다음 순서로 고정하며 먼저 실패한 한 경계만 권위를 가진다.

1. stop result가 exact echo할 base correlation identity shape를 검증한다. 이는 기존 v1 type/domain을 만족하는 payload `request_id`, envelope `message_id`, envelope `session_id`와 `metadata.server_connection_generation`의 완전한 quartet다. candidate marker는 식별됐지만 이 quartet 중 하나라도 누락·잘못된 타입·허용 범위 밖이면 ordinary lane으로 fall through하지 않고 queue offer, barrier, result factory, wire `command_result`와 StopCommand를 모두 호출하지 않은 채 diagnostics-only `invalid_stop_control_correlation_identity`로 no-wire quarantine/drop한다. live Python tracker가 있다면 authoritative result를 받을 수 없으므로 full dual-process reset 전 유지한다.
2. base quartet가 유효하면 exact dedupe key를 먼저 조회한다. 기존 LIVE/tombstone이면 나머지 payload validation보다 duplicate audit-only disposition이 우선한다.
3. 새 distinct identity이면 wire result를 만들기 전에 dedupe LIVE/tombstone slot을 원자적으로 예약한다. capacity가 없으면 diagnostics-only `stop_control_dedupe_capacity_exhausted` no-wire branch가 우선한다.
4. 예약된 candidate에 대해 `command=stop`, `request_kind=stop_control_v1`, `operation=stop_ai`, capability, source/deadline/input-event를 포함하되 `target_scope`와 target quartet를 제외한 general control profile의 shape/exact 값을 검증한다. 실패하면 exact request quartet를 echo하는 `invalid_control_profile` no-mutation result다.
5. request envelope session과 accepted session을 비교하고, 다음으로 request `metadata.server_connection_generation`과 accepted server generation을 비교한다. 각각 첫 mismatch를 `session_mismatch`, `server_generation_mismatch`로 닫는다.
6. well-typed `deadline_ms`의 expiry를 검사해 `deadline_exceeded`로 닫는다.
7. `target_scope` enum을 검사해 `invalid_target_scope`로 닫는다.
8. declared scope에 따른 target quartet의 required/forbidden presence와 type/domain을 검사해 `invalid_target_fields`로 닫는다.
9. full profile이 유효한 뒤 distinct stop in-flight를 검사해 `stop_control_in_flight`로 닫거나 valid queue offer로 진행한다.

위 4-9의 terminal wire result는 이미 예약한 exact identity를 terminal tombstone으로 남긴다. 따라서 target-scope/field reason이 `invalid_control_profile`에 흡수되지 않고, duplicate/capacity/base-identity no-wire branch도 wire terminal과 경쟁하지 않는다. 두 discriminator key가 모두 없고 `command=stop`만 있는 기존 GUI/direct ordinary request는 이 새 control discriminator가 아니며 pre-existing ordinary path를 그대로 따른다. 이 규칙은 malformed public control의 우회 실행을 막기 위한 것이지 기존 ordinary `stop`의 의미를 바꾸기 위한 것이 아니다.

`chatclef_stop_control_v1`은 JSON boolean literal `true`일 때만 지원으로 인정한다. 문자열 `"true"`, 숫자 `1`, 누락 또는 다른 값은 지원이 아니다. `BridgeMessageType`, protocol version, top-level schema `oneOf`, common DTO를 늘리지 않는다. capability를 광고하지 않은 구형 Fabric client에는 stop control을 보내지 않고 local typed reason `stop_control_capability_unavailable`로 정직하게 거절한다. companion protocol 문서에는 이 negotiated metadata profile과 호환성 표만 추가한다.

기존 registry/bridge 문서의 “새 Java 또는 wire 변경 없음” 범위와 충돌한다면, 이 문서가 오직 `stop_control_v1`에 한해 기존 metadata/data 확장 지점, 위 capability와 LAVI-owned Fabric control packages를 추가하는 좁은 후속 결정이다. common DTO/message type/protocol version, ordinary command 의미와 다른 backend에는 이 override가 미치지 않는다. rollback unit은 §16의 C-E다.

### 10.2 Control request and target scope

stop control도 독립적인 `request_id`와 envelope `message_id`를 갖지만, Python ordinary active owner에는 등록하지 않는다. `command_request` payload는 다음을 가진다.

```text
request_id=<stop control request id>
command=stop
source=<trusted typed source>
deadline_ms=<bounded stop-control deadline>
metadata.request_kind=stop_control_v1
metadata.operation=stop_ai
metadata.input_event.source
metadata.input_event.provider_id
metadata.input_event.event_kind
metadata.input_event.final
metadata.input_event.event_id
metadata.server_connection_generation
metadata.target_scope=tracked_command | current_global_automation

required only when target_scope=tracked_command:
  metadata.target_request_id
  metadata.target_command_message_id
  metadata.target_session_id
  metadata.target_server_connection_generation
```

`metadata.input_event`는 기존 submission request factory가 쓰는 canonical nested provenance 구조와 exact field names를 재사용한다. receipt/registry token/nonce는 payload에 들어가지 않는다. 이 provenance는 Java trust authority가 아니라 bounded audit correlation이다.

유효 phrase/provenance/event 검증 뒤 receipt를 발급한다. 그 다음 기존 ordinary-command lock과 같은 권위의 stop-admission lock 아래에서 다음을 하나의 원자적 commit으로 수행한다.

```text
live session/capability and no-other-stop 재검증
+ current ordinary context 확인
+ complete target snapshot 가능 여부와 scope 확정
+ receipt spend
+ send-eligible이면 stop tracker 등록
+ send-eligible이면 Python stop-control admission barrier close
```

local preflight rejection도 같은 lock 안에서 receipt를 영구 spend한 뒤 terminal로 끝나며 tracker/barrier/scope를 만들지 않는다. send-eligible branch는 lock을 놓기 전에 아래 scope 중 정확히 하나와 immutable snapshot을 확정한다. socket send 자체는 lock 밖에서 하되 tracker와 barrier가 먼저 보이므로 ordinary command가 그 사이에 끼어들 수 없다.

send call이 byte write 전의 확정적인 `REJECTED_BEFORE_WRITE`를 반환하면 같은 tracker object/token CAS로 tracker와 stop barrier를 함께 해제할 수 있다. claim은 spent 상태로 남는다. bytes accepted 여부가 불명확한 exception/timeout은 이 경로를 사용할 수 없고 `CONTROL_SEND_UNKNOWN_QUARANTINED`가 된다.

```text
tracked_command:
  exact pending/active Python command context의 complete immutable snapshot이 있음
  -> 네 target identity field 모두 필수

current_global_automation:
  Python ordinary context가 없거나 complete retirement snapshot을 만들 수 없음
  -> 네 target identity field 모두 금지
```

Python active request가 없거나 retirement identity가 불완전하다는 사실을 ChatClef idle 증거로 쓰지 않는다. target 없는 scope는 바로 그 untracked/idle/인게임 automation까지 기존 global StopCommand로 중지하기 위한 명시적 emergency-stop 정책이다. incomplete Python identity는 원래 command 결과의 자동 retirement를 포기하게 만들 뿐, 신뢰된 global stop 자체를 막지 않는다.

Java는 `END_CLIENT_TICK`에서 scope를 다음처럼 처리한다.

- `tracked_command`: 네 target field는 type/shape가 모두 well-formed여야 한다. exact current context와 일치하면 그 context를 retirement owner로 capture한다. well-formed이지만 값이 stale/mismatched이거나 target이 이미 retired/replaced됐으면 현재 Java context를 다시 원자 capture하거나 none으로 기록하고 global stop은 계속한다.
- `current_global_automation`: target field가 없어야 한다. tick에서 현재 Java ordinary context가 있으면 그 context를 원자적으로 capture해 user-stop retirement owner로 삼고, 없어도 current engine automation을 대상으로 계속한다.
- pending context가 있으면 dispatch 불가 `CANCEL_SEND_IN_FLIGHT`로 전이하고 context를 보존한다. 즉시 물리적으로 제거하지 않는다.
- active context가 있으면 bound root와 user-stop marker를 StopCommand 전에 원자적으로 묶는다.
- 두 scope 모두 위 context 준비가 성공하면 기존 registered StopCommand를 정확히 1회 호출한다. ordinary context가 전혀 없는 global scope도 호출 1회다.

trusted global emergency stop의 authorization anchor는 `event_id` claim, accepted session/server generation, non-replay deadline과 Python/Java의 별도 stop-control admission barrier다. unresolved ordinary owner가 있으면 그 owner의 기존 admission gate도 독립적으로 유지된다. Python은 send-eligible commit부터 terminal/unknown까지 새 ordinary command를 보내지 않고, Java는 stop entry를 ordinary dispatch보다 먼저 처리한다. tracked fields는 original-command retirement correlation을 강화하지만 global engine mutation의 authorization은 아니다. `current_global_automation`과 replaced tracked target 모두 2초 안에 client tick이 포착한 현재 global automation을 의도적으로 중지한다.

초기 `deadline_ms`는 Python submit 시각 기준 `now + 2000 ms`로 고정한다. control은 reconnect queue에 보존하거나 재생하지 않는다. Java의 첫 실행 판단 client tick에서 deadline을 넘었으면 기존 v1 `status=deadline_exceeded`, `error_code=deadline_exceeded`로 종료한다. deadline 안에 실행을 시작한 뒤의 terminal 검증은 별도 20-later-tick 한계가 소유한다.

Java stop queue는 in-flight 최대 1개다. duplicate/tombstone key는 exact `(session_id, server_connection_generation, request_id, message_id)`이며 immutable request fingerprint와 함께 current accepted generation에서 최대 `4096`개를 보존한다. 같은 key가 LIVE 또는 terminal tombstone에 이미 있으면 payload 일치 여부와 관계없이 두 번째 queue offer, barrier 생성, `command_result` 생성/전송과 StopCommand 실행을 모두 하지 않고 bounded audit-only drop으로 끝낸다. 특히 LIVE duplicate에 `duplicate_control` rejection result를 보내 원래 tracker를 선점하게 해서는 안 된다. 원래 control owner와 그 한 terminal/result-delivery lifecycle은 그대로 유지한다. base-valid 새 distinct identity는 profile이 나중에 wire rejection으로 끝날 때도 exactly-once tombstone을 보장할 slot을 모든 나머지 validation보다 먼저 확보해야 한다. slot을 확보한 뒤에만 `invalid_control_profile`, session/generation/deadline, target scope/fields 또는 distinct `stop_control_in_flight` wire result를 만들 수 있다. registry가 `4096`개로 가득 차 새 identity를 보존할 수 없으면 queue offer, barrier, `command_result` 생성/전송과 StopCommand 실행을 모두 하지 않고 diagnostics-only `stop_control_dedupe_capacity_exhausted`로 audit-only drop한다. 같은 frame이 다시 와도 wire result를 만들지 않으며 기존 tracked identity의 lifecycle을 바꾸지 않는다. 이 no-wire 결과 때문에 Python의 해당 새 stop tracker/barrier는 해제 증거를 받지 못하고 full dual-process reset 전 quarantine에 남는다. 자동 eviction으로 replay 권한을 되살리지 않으며, accepted generation 교체 또는 정상 shutdown/test reset만 이전-generation registry를 폐기하고 stale socket callback은 `java_socket_generation` fence가 계속 차단한다.

WebSocket callback의 valid queue offer와 `JavaStopControlAdmissionBarrierToken` 생성은 같은 Java owner lock 안의 한 commit이다. queue offer가 실패하면 barrier token도 없어야 한다. 성공한 token은 exact control/session/server-generation/socket-generation identity에 묶이고 ordinary queue offer와 dispatcher가 모두 확인한다. tick dispatcher가 stop entry를 poll해도 token을 제거하지 않으며 `QUEUED -> EXECUTING -> VERIFYING` 또는 `CANCEL_SEND_IN_FLIGHT`/quarantine 동안 계속 유지한다. release 조건은 §11.3에 고정한다.

### 10.3 Python and Java trust boundaries

Python trusted-ingress registry, common eligibility owner와 STOP one-shot claim registry만 source provenance와 opaque receipt의 semantic authority다. receipt는 spend 전에 Python process를 벗어나지 않으며, Java는 직렬화된 source/provider/event 문자열이 실제 adapter에서 왔는지 증명할 수 없다.

Java가 권위 있게 검증하는 것은 다음뿐이다.

```text
handshake capability
envelope and command-request schema
request_kind=stop_control_v1
operation=stop_ai
command=stop
request/message/session/generation identity
target_scope discriminator and field presence
tracked target schema and best-effort exact retirement correlation
duplicate request/message identity
deadline
```

`metadata.input_event`는 bounded audit correlation에만 사용한다. Java 거절 사유로 `invalid_provenance` 또는 `invalid_claim`을 만들지 않는다.

### 10.4 Connection generation authority

Python server generation과 Java-local socket generation은 서로 다른 counter이며 같은 숫자라고 가정하지 않는다.

```text
server_connection_generation:
  owner = Python FabricChatClefConnectionOwnership
  transport = accepted handshake_ack.payload.connection_generation
  use = wire identity, target identity, Python result acceptance

java_socket_generation:
  owner = Java WebSocket reconnect runtime
  transport = Java process-local only unless diagnostic data explicitly names it
  use = stale callback/socket fencing inside Java
```

Java `FabricChatClefSessionGuard`는 accepted handshake ACK의 `server_connection_generation`을 session ID와 함께 저장해야 한다. rejected/duplicate handshake ACK가 현재 accepted 값에 덮어쓰면 안 된다. stop request 자체의 `server_connection_generation`은 이 저장값 및 envelope session과 일치해야 한다. `tracked_command`의 `target_server_connection_generation`은 well-formed correlation snapshot이며 current value와 다르면 exact retirement miss로 기록할 뿐, 이미 유효한 global stop request를 거절하지 않는다.

`java_socket_generation`을 wire의 `connection_generation`처럼 보내거나 Python server generation과 비교하지 않는다. stop-profile result와 original cancellation result의 `data.connection_generation`은 기존 Python matcher 호환을 위해 server-assigned 값을 사용하고, 필요하면 `data.java_socket_generation`을 이름이 분리된 diagnostics-only 필드로 추가한다.

Python server restart, Java reconnect, rejected duplicate handshake 때문에 두 counter가 달라도 위 권위 분리로 valid current scope는 통과하고 이전 session/generation control은 fail-closed해야 한다.

### 10.5 Control result identity and demux

stop control 결과도 기존 `command_result` envelope를 사용한다. 기존 ordinary result handler가 먼저 소비하게 두지 않고, Python result demux가 profile field보다 exact live stop-control tracker의 request/correlation/session/server-generation identity를 먼저 검사한다. identity가 matching하면 marker가 누락·부분·오타여도 stop handler가 독점해 strict result-profile validation을 수행하고, malformed 결과는 `UNKNOWN` quarantine으로 끝내며 ordinary owner/barrier를 해제하지 않는다. live tracker가 없더라도 `data.request_kind=stop_control_v1` 또는 `data.operation=stop_ai` 중 하나가 exact하면 stale/foreign stop result로 audit-only drop하고 ordinary handler에 넘기지 않는다. exact live tracker도 exact stop marker도 없는 결과만 pre-existing ordinary result demux로 간다.

wire result를 만들 수 있을 만큼 base correlation identity가 검증된 stop request라면 모든 stop-control result는 그 거절 또는 실행 대상 request의 exact identity를 echo한다. top-level `request_id`는 원본 `CommandRequestDTO.request_id`, `correlation_id`는 원본 request envelope `message_id`, result envelope `session_id`는 원본 request envelope `session_id`, `data.connection_generation`은 원본 request의 `metadata.server_connection_generation`이다. 이 규칙은 pre-queue `session_mismatch`와 `server_generation_mismatch`에도 동일하게 적용한다. Java가 validation 시점에 들고 있던 current accepted session/generation은 이 quartet를 덮어쓰지 않고 diagnostics-only `accepted_session_id_at_validation`과 `accepted_server_connection_generation_at_validation`로만 기록한다. 따라서 Python은 거절된 request의 exact live tracker를 찾을 수 있고, guard의 current accepted identity를 stop result의 권위 identity로 오인하지 않는다.

`stop_command_exception`의 `matching`은 resolution `none`일 때 before가 `none`, context resolution일 때 before가 `pending|active`라는 뜻이다. no-context branch는 synchronous StopCommand가 정상 return하면 즉시 success profile이고, throw하면 `stop_command_exception`이므로 no-context `verification_timeout` profile은 없다. `original_cancel_send_failed`는 original cancellation의 bounded retry가 최종 실패 또는 exhaustion에 도달했고 control transport는 아직 wire result를 보낼 수 있을 때만 허용한다. retry budget이 남은 단일 `ASYNC_SEND_FAILED`는 terminal reason이 아니며 같은 immutable original result의 retry state에 머문다. captured context의 `verification_timeout`은 terminal payload commit 전까지 original delivery/retirement success predicate가 아직 불완전하고 control transport가 result를 보낼 수 있을 때만 허용한다. result transport가 terminal payload commit 전에 detach되면 새 wire `control_reason`을 조작하지 않고 diagnostics-only `connection_detached_after_execution` disposition과 local quarantine으로 끝낸다. completed/proved-no-mutation/unknown payload가 이미 commit된 뒤의 detach 또는 control-result send failure도 committed status/reason을 바꾸지 않고 delivery/quarantine state로만 기록한다.

`target_observation_failed`는 context read/capture, pending non-dispatchable reservation 또는 owner-lock/CAS 결과를 신뢰할 수 없을 때 StopCommand를 호출하지 않고 사용하는 유일한 pre-mutation uncertainty reason이다. 이는 proved-no-mutation rejection이 아니므로 result가 `SENT`여도 Java/Python stop barrier와 ordinary owner를 해제하지 않는다.

Java result factory는 immutable payload commit 전에 closed enum, required/null field, full requested/resolved identity, reason/profile와 tick relation을 검증한다. Python stop result handler도 독립적으로 같은 matrix를 검증한다. 알려지지 않은 authorization field, missing required field, reason과 모순되는 status/outcome/scope/resolution/state/delivery/invocation/tick 또는 partial identity가 하나라도 있으면 그 payload를 completed나 proved-no-mutation rejection으로 받아들이지 않는다. Python은 matching live tracker를 `UNKNOWN` quarantine에 유지하고 ordinary owner와 양쪽 barrier를 clear하지 않으며 stopped/rejected terminal 발화를 만들지 않는다.

Java 내부 factory가 자기 payload의 모순을 발견하면 `target_observation_failed`나 `stop_command_exception`처럼 사실과 다른 wire reason으로 치환하지 않는다. 모순 payload와 대체 wire result를 모두 보내지 않고 diagnostics-only `result_profile_construction_failed` disposition을 한 번 기록한 뒤 exact control identity를 local quarantine에 둔다. pre-queue이면 dedupe identity를 quarantine/tombstone 상태로 유지하고, queue/barrier 생성 뒤이면 그 Java barrier와 owned context도 유지한다. Python은 result를 받지 못하므로 기존 stop tracker/barrier를 유지한다. 어느 경우도 full dual-process reset 전 재실행·barrier release·stopped/rejected 발화가 없다.

Java의 stop-control result도 async send submission 수락만으로 `SENT`가 아니다. terminal owner는 첫 send 전에 `completed`, proved-no-mutation `rejected/deadline_exceeded` 또는 `unknown` 중 정확히 하나의 immutable payload를 CAS로 한 번만 commit한다. exact committed payload에 대한 기존 bounded delivery retry만 허용하며 StopCommand, context capture, control execution 또는 payload classification은 반복하지 않는다. valid queue offer가 Java barrier token을 만든 branch에서 matching `FabricChatClefCommandResultSendCompletion=SENT`가 그 barrier의 release 증거가 되려면 이미 committed된 payload 자체가 `completed/stopped` 또는 proved-no-mutation rejection/deadline이어야 한다. pre-queue wire rejection에는 Java token이 없으며 matching Python result acceptance만 Python barrier를 해제한다. committed `unknown`의 send가 늦게 `SENT`가 되어도 barrier release 권위가 아니다.

matching original cancellation `SENT`가 stop-control terminal payload commit 전에 `VERIFYING` owner에 도착하면 exact context를 retire하고 success predicate를 충족시켜 유일한 payload를 `completed/stopped`로 commit할 수 있다. payload가 한 번 commit된 뒤 도착한 original evidence는 그 exact ordinary context/owner만 retire할 수 있을 뿐 stop-control payload를 바꾸거나 두 번째 terminal을 만들지 않는다. 따라서 `unknown` payload가 commit되거나 전달된 뒤에는 late original `SENT`로 completed를 새로 발행하지 않으며 stop-control barrier는 full dual-process reset 전까지 quarantine이다. completed/proved-no-mutation payload의 send completion만 늦은 경우에는 같은 immutable payload와 exact barrier token의 CAS로 release를 마칠 수 있다.

ordinary result handler가 stop control result를 교차 소비해서는 안 된다. `tracked_command`가 frozen한 Python target에 대해서는 stop-admission coordinator가 matching `completed/stopped` control result를 받은 같은 command lock 안에서 다음 CAS를 모두 통과할 때만 그 exact frozen Python owner를 `cancelled/user_stop_requested`로 retire할 수 있다: current owner object/token이 frozen snapshot과 동일, control request/session/server-generation/correlation이 동일, requested target echo quartet가 frozen snapshot과 동일, `data.target_resolution=exact`, resolved target의 request/message/session/server-generation quartet가 requested/frozen identity와 전부 동일, `stop_command_invoked=true`, `original_result_delivery=sent`, target state가 retired다. original `cancelled` result가 먼저 정상 retire했다면 이 CAS는 no-op이고, newer/different owner는 절대 clear하지 않는다.

`target_resolution=captured_current` 또는 `none`은 stale requested target의 retirement miss이지 frozen owner A의 retirement 증거가 아니다. Java가 replacement B를 capture했다면 B의 exact original cancellation result handler만 B를 retire할 수 있고, control result로 A나 B를 대리 clear하지 않는다. matching completed/stopped control terminal은 stop-control barrier를 해제할 수 있지만 unresolved frozen owner A의 기존 ordinary-owner admission gate/quarantine은 A 자체의 authoritative terminal까지 남는다. `rejected/unknown` control result는 ordinary owner를 clear하지 않는다.

초기 typed `control_reason` 집합은 다음으로 닫는다. 알려지지 않은 문자열은 Python에서 success로 승격하지 않고 `unknown`으로 처리한다.

```text
success:

  tracked_active_stopped
  tracked_target_replaced_current_pending_stopped
  tracked_target_replaced_current_active_stopped

  global_active_stopped

  invalid_control_profile

```

base correlation quartet가 invalid인 candidate, exact duplicate/tombstone identity와 dedupe-capacity에 admit할 수 없는 새 identity는 `control_reason`을 가진 wire terminal이 아니다. `invalid_stop_control_correlation_identity`, `duplicate_control_live`, `duplicate_control_tombstoned`, `duplicate_control_payload_mismatch`, `stop_control_dedupe_capacity_exhausted` 같은 bounded diagnostic disposition으로만 기록하고 response factory/result sender/Python result demux를 호출하지 않는다. terminal payload commit 전 transport detach도 diagnostics-only `connection_detached_after_execution` disposition으로 기록하며 대체 wire result를 만들지 않는다. 원래 result sender가 소유한 동일 immutable result의 bounded delivery retry만 허용하며, inbound replay가 result resend나 control 재실행을 유발하지 않는다.

pre-common-gate reason인 `untrusted_stop_provenance`와 `invalid_stop_event_id`는 diagnostics-only이며 새 Minecraft response/publisher를 만들지 않는다. common proof 뒤의 Python-local pre-send reason은 wire result와 섞지 않는다: `unsafe_stop_phrase`, `duplicate_or_spent_stop_claim`, `stop_claim_capacity_exhausted`, `stop_control_in_flight`, `stop_control_capability_unavailable`, `bridge_disconnected`, `control_send_rejected`, `control_send_unknown`. 각 admitted-request reason은 §12의 truthful response category에 고정하고, unknown/rejected를 stopped로 바꾸지 않는다.

Wire mapping은 고정한다: success reason은 `completed/true/null`, `deadline_exceeded`는 `deadline_exceeded/false/deadline_exceeded`, 나머지 no-mutation reason은 `rejected/false/invalid_request`다. `target_observation_failed`와 `stop_command_exception`은 `unknown/false/internal_error`, 나머지 post-mutation unknown reason은 `unknown/false/null`이다. `error_code`는 이 기존 v1 값 외에 새 enum을 추가하지 않는다.

## 11. Java client-tick execution contract

### 11.1 Thread boundary

```text
WebSocket callback thread
  -> minimally parse stop-control candidate discriminator
  -> validate base request/message/session/server-generation quartet shape
     | invalid -> diagnostics-only no-wire quarantine/drop
  -> under dedupe owner lock, lookup exact key
     | LIVE/tombstone -> audit-only duplicate drop
  -> reserve new identity slot before any wire-result-eligible validation
     | capacity exhausted -> diagnostics-only no-wire drop
  -> validate remaining envelope/common schema, capability and general profile
  -> validate current session, current generation and deadline in that order
  -> validate target_scope, then target-field presence/type
  -> full-profile distinct in-flight rejection OR bounded stop queue offer
     | wire rejection -> immutable result commit/send + terminal tombstone
  -> no Minecraft API, no StopCommand, no task/path/input mutation

Minecraft END_CLIENT_TICK
  -> process one stop control before ordinary pending dispatch and active early-return
  -> revalidate session/generation/deadline/scope
  -> tracked scope: resolve exact target, otherwise atomically capture current context/none
     OR global scope: atomically capture current Java ordinary context if present
     | context read/capture or pending-reservation owner CAS cannot produce a
       trustworthy snapshot -> do not invoke StopCommand; commit
       unknown/target_observation_failed and quarantine
  -> pending context: make non-dispatchable and retain as CANCEL_SEND_IN_FLIGHT
     OR active context: CAS-bind user_stop_requested marker and root ownership
     OR global scope with no ordinary context: continue without original-result owner
  -> invoke existing registered StopCommand exactly once
  -> when an ordinary context exists, emit original cancelled result
     and retain the context until SendCompletion=SENT
  -> observe bounded retirement and emit separately correlated stop-control result
```

새 background thread, timer, `sleep`, polling executor를 만들지 않는다. captured ordinary context retirement 확인이 한 tick 이상 필요하면 stop control owner가 제한된 client-tick state machine으로 소유한다. 초기 상수는 `STOP_VERIFY_MAX_LATER_TICKS=20`으로 고정하며 tick 20까지 그 captured-context success predicate를 완성하지 못하면 control outcome은 `unknown`이고 자동 재실행하지 않는다. no-context branch는 기다리지 않는다. synchronous StopCommand 정상 return은 같은 tick의 success이고 throw는 같은 tick의 `stop_command_exception`이다.

matching 또는 어느 scope에서든 capture된 active command가 있으면 `user_stop_requested` marker를 `StopCommand` 호출 전에 같은 control/command identity에 CAS로 원자적으로 묶는다. 정지 과정에서 Task finish/stop callback이 동기적으로 발생해도 classifier가 일반 실패로 먼저 소비하지 않게 하기 위해서다. marker binding 또는 bound-root match에 실패하면 그 context를 original-cancellation owner로 사용하지 않지만, 이미 권한이 확정된 global StopCommand 자체는 정확히 1회 실행하고 control outcome을 `unknown/user_stop_marker_bind_failed`로 제한한다. 정리에서 marker가 아직 terminal에 소비되지 않았다면 같은 owner가 제거하되, 다른 command marker는 건드리지 않는다.

pending context는 StopCommand 호출 전에 `PENDING -> CANCEL_SEND_IN_FLIGHT`로 원자 전이해 dispatch할 수 없게 만든다. 원래 context는 `cancelled` result의 retry/terminal owner이므로 `SendCompletion=SENT` 전에 물리적으로 제거하지 않는다. pending만 취소해도 pre-existing idle/untracked automation이 계속될 수 있으므로 global stop 의미를 지키기 위해 pending 분기에서도 StopCommand를 정확히 1회 호출한다.

context read/capture 자체, pending reservation CAS 또는 그 owner-lock 결과를 신뢰할 수 없으면 active-marker branch로 추정하거나 global no-context로 downgrade하지 않는다. `stop_command_invoked=false`, `target_observation_failed`로 닫고 양쪽 stop barrier를 quarantine한다. 반대로 active context identity는 확정됐고 marker bind만 명시적으로 실패한 경우에만 위 `user_stop_marker_bind_failed` branch가 StopCommand 1회를 허용한다.

### 11.2 Mutation owner

gameplay mutation owner는 기존 `StopCommand -> AltoClef.stop()`뿐이다. 새 bridge code는 다음을 직접 호출하거나 복제하지 않는다.

```text
TaskRunner global stop implementation
Baritone forceCancel
input override clearAllKeys
individual movement/attack/use keys release
arbitrary Task.stop()
```

이 내부 정리는 `AltoClef.stop()`이 이미 소유한다. bridge는 command execution, correlation, verification과 result 전송만 소유한다.

### 11.3 Relationship to ordinary command queue

- ordinary queue의 pending/active 최대 1개 규칙은 그대로다.
- stop control queue/tracker는 Python과 Java 각각 최대 1개의 in-flight stop만 허용한다.
- stop 이외의 control 또는 두 번째 일반 command를 허용하지 않는다.
- Python은 send-eligible claim commit과 동시에 별도 stop-control admission barrier를 닫는다. 확정적인 pre-send/local rejection은 barrier를 열지 않고, socket outcome이 unknown이거나 send가 수락된 뒤에는 아래 authoritative terminal 또는 full dual-process reset 전까지 새 command를 통과시키지 않는다.
- Java는 valid stop queue offer와 같은 lock commit에서 exact `JavaStopControlAdmissionBarrierToken`을 만든다. ordinary WebSocket queue offer와 client-tick ordinary dispatcher는 둘 다 이 token이 있으면 새 ordinary admission/dispatch를 막는다.
- stop control은 ordinary pending dispatch와 active early-return보다 먼저 평가된다.
- tick dispatcher가 stop queue entry를 poll한 사실은 Java barrier release가 아니다. token은 `EXECUTING`, `VERIFYING`, original `CANCEL_SEND_IN_FLIGHT`와 result-delivery 단계 전체에서 같은 identity로 유지된다.
- valid queue offer가 만든 Java barrier는 exact token CAS와 matching stop-control result `SendCompletion=SENT`가 있고, 그 result가 (a) queue 이후 tick revalidation에서 gameplay mutation 전 `rejected/deadline_exceeded`임이 증명됐거나 (b) `completed/stopped`이고 captured ordinary context가 있다면 그 exact original cancellation `SENT`와 retirement까지 증명된 경우에만 해제한다. no-context completed도 StopCommand 정상 completion과 matching control result `SENT` 뒤에 해제한다. pre-queue rejection에는 Java barrier가 없다.
- result send가 불명확하거나 post-mutation outcome이 `unknown`이면 Java token은 quarantine으로 유지한다. stop-control terminal payload가 아직 commit되지 않았다면 exact late original cancellation `SENT`가 success predicate를 완성한 뒤 유일한 completed payload를 만들 수 있다. 이미 committed된 completed/proved-no-mutation payload의 exact late control-result `SENT`만 같은 token CAS로 barrier release를 마칠 수 있다. committed `unknown`은 late original/control `SENT`로 재분류하거나 해제하지 않으며 full dual-process owner reset만 stop-control barrier를 없앤다.
- Python의 stop-control barrier도 matching proved-no-mutation rejection/deadline 또는 matching `completed/stopped` terminal에서만 해제하며 `UNKNOWN`은 해제 권위가 아니다. barrier가 해제돼도 unresolved ordinary owner가 있으면 기존 ordinary-owner admission gate는 그대로 닫혀 있다.
- Java send-completion callback과 Python result acceptance 사이에는 전역 total order가 없다. 각 process는 자기 authoritative evidence와 exact token으로 local barrier를 독립 CAS하며 어느 쪽이 먼저 열려도 반대쪽의 닫힌 barrier가 그 process의 ordinary admission을 계속 차단한다. peer barrier가 열렸을 것이라는 추정으로 local barrier를 선제 해제하지 않는다.

### 11.4 Original command terminal

현재 stopped active task가 `failed/matching_task_stopped`로 분류되는 경로는 사전에 CAS-bind된 사용자 stop identity가 일치할 때만 다음으로 좁게 변경한다. pending 또는 global scope에서 capture된 ordinary context도 같은 terminal 의미를 사용한다.

```text
request_id=<original pending or active request>
ok=false
status=cancelled
error_code=null
message=<bounded cancellation message>
data.result_reason=user_stop_requested
```

일반적인 예외, 자연 종료, timeout, connection detach는 기존 classifier 의미를 유지한다. 늦게 온 original terminal은 audit에는 남겨도 새로운 active command를 clear해서는 안 된다.

Java ordinary context 전이는 다음으로 고정한다.

```text
PENDING | ACTIVE
  -> USER_STOP_CLAIMED
  -> CANCEL_SEND_IN_FLIGHT
  -> RETIRED only after matching SendCompletion=SENT

ASYNC_SEND_FAILED while attempts remain and same session/generation is live
  -> keep CANCEL_SEND_IN_FLIGHT
  -> retry only the same immutable result delivery

detach | retry exhausted
  -> CANCEL_RESULT_QUARANTINED
  -> no further automatic retry
  -> command와 StopCommand 재실행 금지
```

`UNKNOWN`, timeout, elapsed wall clock, generic reconnect, session/generation 교체, Python active clear와 status snapshot만으로 context/barrier를 해제하지 않는다. stop-control barrier와 ordinary-owner gate는 서로 다른 state다. 초기 구현의 authoritative retirement/release evidence는 다음으로 닫는다.

```text
Java context release:
  exact registered cancellation send-attempt token
  + full request/message/session/server-generation identity
  + matching FabricChatClefCommandResultSendCompletion=SENT
  + same context object CAS

Java stop-control barrier release:
  exact JavaStopControlAdmissionBarrierToken CAS
  + matching stop-control result SendCompletion=SENT
  + proved-no-mutation rejection/deadline
    OR completed/stopped success predicate including captured-context retirement
  + committed unknown payload is never eligible

Python stop-control barrier release:
  matching proved-no-mutation rejection/deadline accepted
  OR matching completed/stopped stop-control terminal accepted

Frozen Python ordinary owner release:
  exact original cancelled result accepted
  OR §10.5 exact-only control-result CAS where
     target_resolution=exact
     AND resolved=requested=frozen request/message/session/server-generation quartet

Captured replacement Java context release:
  only that replacement context's exact original cancellation SENT/CAS
  never the stale requested target or generic control result
```

stop-control terminal payload commit 전에 늦게 도착한 exact original cancellation `SENT`는 위 context CAS를 통과해 success predicate를 완성할 수 있고, 그 뒤 유일한 completed payload를 commit한다. payload commit 뒤의 late original `SENT`는 exact Java context와 matching Python ordinary owner만 retire하며 이미 committed된 stop-control status/reason을 바꾸거나 두 번째 result를 만들지 않는다. 이미 committed된 completed/proved-no-mutation payload의 exact control-result `SENT`는 barrier CAS를 마칠 수 있지만 committed `unknown` payload의 original/control `SENT`는 Java/Python stop-control barrier를 해제하지 못한다. 그 증거가 없으면 해당 stop-control barrier quarantine은 owner-instance 수명 동안 유지한다. stale requested A 대신 replacement B가 정상 취소된 경우 terminal commit 전이면 completed payload를 만들고 stop-control barrier를 정상 해제할 수 있지만, A의 ordinary-owner gate는 A의 별도 authoritative retirement 전까지 유지한다. 초기 범위에는 in-process force-clear나 generic reconnect recovery가 없다. 유일한 operator reset은 LAVI Python process와 Minecraft/Fabric Java process를 둘 다 완전히 종료한 뒤 새 owner graph로 시작하는 full dual-process restart다. 한쪽만 재시작하면 recovery 증거가 아니며 남아 있는 쪽의 queue/barrier가 계속 admission을 막아야 한다. 테스트는 두 owner graph의 폐기와 새 instance 생성을 명시적으로 검증한다.

### 11.5 Stop success predicate

`completed/stopped`는 다음 분기별 predicate가 모두 참일 때만 허용한다.

```text
PENDING context:
  tracked exact match OR any-scope atomic current capture
  AND context became non-dispatchable before ordinary dispatch
  AND registered StopCommand invoked exactly once without command exception
  AND original cancelled result FabricChatClefCommandResultSendCompletion=SENT
  AND context removed only after SENT and is neither pending nor active afterward
  AND all facts are observed by STOP_VERIFY_MAX_LATER_TICKS=20

ACTIVE context:
  tracked exact match OR any-scope atomic current capture
  AND bound root ownership matched
  AND user_stop_requested marker CAS-bound before StopCommand
  AND registered StopCommand invoked exactly once without command exception
  AND target no longer occupies Java active queue ownership
  AND bound target root is no longer the current owned root
  AND original cancelled result FabricChatClefCommandResultSendCompletion=SENT
  AND all facts are observed by STOP_VERIFY_MAX_LATER_TICKS=20

NO LAVI ordinary context:
  target_scope=current_global_automation OR tracked target resolved to none
  AND request target-field presence matched its declared scope
  AND client tick atomically observed no pending/active ordinary context
  AND registered StopCommand invoked exactly once
  AND synchronous AltoClef.stop()/StopCommand completion returned without exception
```

`sendText()`가 async send를 수락했다는 사실만으로 `SENT`로 보지 않는다. ordinary context가 있을 때 later send completion이 `ASYNC_SEND_FAILED`, connection detached 또는 retry exhausted면 stop-control result를 `completed/stopped`로 만들지 않는다. 원래 request는 non-dispatchable 상태로 보존하고 Python ordinary admission은 authoritative retirement를 받을 때까지 닫아 둔다. Java ordinary context가 없는 global scope에서는 original result가 없으므로 `not_applicable`이고 registered StopCommand의 정상 completion이 terminal authority다.

하나라도 확정할 수 없으면 `stopped`라고 말하지 않는다. `StopCommand`가 내부적으로 소유하는 개별 key/path flag를 bridge가 중복 조작하거나 성공 predicate용 새 mutable global로 복제하지 않는다. command exception, verification timeout 또는 terminal payload commit 전 original cancellation delivery ambiguity는 control transport가 sendable이면 immutable `unknown` result를 한 번 commit하고 전송한다. payload commit 전에 connection이 detach되면 wire reason을 만들 수 없으므로 diagnostics-only quarantine으로 종료한다. 이미 commit된 stop-control payload의 delivery ambiguity는 status/reason을 바꾸지 않고 해당 delivery/barrier만 quarantine한다. 기존 outbox가 동일 original result identity의 bounded delivery retry를 수행할 수는 있지만 StopCommand, pending의 non-dispatchable 전이 또는 stop control 실행 자체는 절대 반복하지 않는다.

## 12. STOP lifecycle and response contract

### 12.1 State model

```text
RECEIVED
  -> COMMON_INPUT_ADMITTED
  -> VALID_EXACT_STOP
  -> SOURCE_ADMITTED
  -> RECEIPT_ISSUED
  -> ATOMIC_ADMISSION_COMMIT
     | local rejection
     -> CLAIM_SPENT -> LOCAL_REJECTED terminal
     |
     | send eligible
     -> SESSION_CAPABILITY_REVALIDATED
        + TRACKED_COMMAND_OR_CURRENT_GLOBAL_AUTOMATION_SNAPSHOTTED
        + CLAIM_SPENT
        + STOP_TRACKER_REGISTERED
        + PYTHON_STOP_CONTROL_ADMISSION_BARRIER_CLOSED
  -> CONTROL_SEND_ATTEMPT
     | REJECTED_BEFORE_WRITE -> TRACKER_AND_STOP_BARRIER_CLEARED terminal
     | CONTROL_SEND_UNKNOWN_QUARANTINED terminal
     | ACCEPTED -> JAVA_VALIDATING
        | INVALID_BASE_CORRELATION_IDENTITY -> AUDIT_ONLY_DROP; NO_WIRE_RESULT
        | DUPLICATE_IDENTITY -> AUDIT_ONLY_DROP; ORIGINAL_CONTROL_FLOW_UNCHANGED
        | DEDUPE_CAPACITY_EXHAUSTED -> AUDIT_ONLY_DROP; NO_WIRE_RESULT
        | PRE_QUEUE_NO_MUTATION_REJECTED -> TERMINAL_RESULT_CANDIDATE
        | VALID_QUEUE_OFFER + JAVA_STOP_BARRIER_CLOSED -> JAVA_QUEUED
  -> CONTEXT_OBSERVATION_AND_CAPTURE
     | TARGET_OBSERVATION_FAILED -> STOP_NOT_INVOKED -> UNKNOWN_RESULT_CANDIDATE
     | PENDING_CONTEXT_CAPTURED | ACTIVE_CONTEXT_CAPTURED | NO_LAVI_CONTEXT
     | TICK_NO_MUTATION_REJECTED -> TERMINAL_RESULT_CANDIDATE
  -> CLIENT_TICK_STOP_EXECUTION
     | USER_STOP_MARKER_BIND_FAILED_BUT_GLOBAL_STOP_EXECUTED
       -> UNKNOWN_RESULT_CANDIDATE
     | STOP_COMMAND_EXCEPTION -> UNKNOWN_RESULT_CANDIDATE
     | STOP_EXECUTED
  -> CANCEL_SEND_IN_FLIGHT -> SENT -> CONTEXT_RETIRED
     | ASYNC_SEND_FAILED_AND_RETRY_REMAINS
       -> CANCEL_SEND_IN_FLIGHT; retry same immutable original result only
     | FINAL_SEND_FAILED_OR_RETRY_EXHAUSTED_WHILE_CONTROL_TRANSPORT_SENDABLE
       -> CANCEL_RESULT_QUARANTINED -> UNKNOWN_RESULT_CANDIDATE
     | CONNECTION_DETACHED_BEFORE_CONTROL_PAYLOAD_COMMIT
       -> CANCEL_RESULT_QUARANTINED
       -> NO_WIRE_CONNECTION_DETACHED_QUARANTINED
     | NO_ORIGINAL_RESULT
  -> VERIFYING; late original SENT may satisfy success only before terminal commit
     | SUCCESS_PREDICATE_COMPLETE -> TERMINAL_RESULT_CANDIDATE
     | VERIFICATION_TIMEOUT -> UNKNOWN_RESULT_CANDIDATE
  -> TERMINAL_RESULT_CANDIDATE | UNKNOWN_RESULT_CANDIDATE
  -> CONTROL_RESULT_PAYLOAD_COMMITTED_ONCE
     status/reason/payload immutable after this CAS
  -> CONTROL_RESULT_READY
  -> CONTROL_RESULT_SEND_IN_FLIGHT
     | ASYNC_SEND_FAILED_AND_RETRY_REMAINS
       -> CONTROL_RESULT_SEND_IN_FLIGHT; retry same committed payload only
     | SENT with committed pre-queue proved-no-mutation payload
       -> REJECTED; JAVA_STOP_BARRIER_WAS_NOT_CREATED
       -> matching Python terminal acceptance releases Python stop barrier
     | SENT with committed queued/tick proved-no-mutation or completed payload
       -> STOPPED | REJECTED
       -> exact Java stop-barrier CAS release
       -> matching Python terminal acceptance releases Python stop barrier
     | SENT with committed unknown payload -> UNKNOWN_QUARANTINED
     | RETRY_EXHAUSTED_OR_DETACHED_OR_AMBIGUOUS
       -> CONTROL_RESULT_DELIVERY_QUARANTINED
       -> committed status/reason remains unchanged
       | exact late SENT with committed completed/proved-no-mutation payload
         -> STOPPED | REJECTED
         -> exact Java barrier CAS only when a queued token exists;
            pre-queue result has no Java token
         -> matching Python terminal acceptance releases Python stop barrier

  any Java result-factory invariant failure before payload commit
     -> RESULT_PROFILE_CONSTRUCTION_QUARANTINED
     -> diagnostics only; no replacement wire result and no automatic replay
```

send-eligible 전이는 동일 `control_request_id`와 server connection generation에 묶인다. Java-local socket generation은 callback fencing에만 사용한다. local rejection은 claim만 spend하고 barrier/control identity를 만들지 않는다. Java pre-queue rejection은 Java barrier를 만들지 않으므로 matching result `SENT` 뒤에도 Java CAS는 없고 Python result acceptance만 Python barrier를 해제한다. valid queue offer 이후 rejection/execution은 exact Java token을 result-delivery 단계까지 유지하고 matching eligible result `SENT` 뒤에만 그 local barrier를 CAS-release한다. `target_observation_failed`, `user_stop_marker_bind_failed`, `stop_command_exception`, original cancellation의 final failure/retry exhaustion 시 control transport가 살아 있는 `original_cancel_send_failed`, `verification_timeout`은 모두 `UNKNOWN_RESULT_CANDIDATE`에서 한 번만 unknown payload를 commit하고 bounded send lifecycle을 거친다. original/control result 모두 retry budget이 남은 definite async failure는 동일 immutable payload의 기존 bounded retry state에 머물며 새 reason/payload를 만들지 않는다. committed unknown이 `SENT`면 `UNKNOWN_QUARANTINED`이고, 어떤 committed payload든 최종 delivery failure/ambiguity면 `CONTROL_RESULT_DELIVERY_QUARANTINED`에서 원래 status/reason을 보존한다. 반면 invalid base correlation identity, dedupe capacity exhaustion, payload commit 전 connection detach와 result-factory invariant failure는 wire payload를 만들 수 없는 diagnostics-only quarantine이다. 어느 quarantine에서도 화살표가 정상 실행으로 다시 이어지지 않으며 reconnect, duplicated voice final event, Chat double submit 또는 timeout이 새 실행을 자동 생성하지 않는다.

accepted 시점에는 `멈췄어요`라고 말하지 않는다. 사용자-facing terminal 응답의 유일한 권위는 matching stop-control result다. original command `cancelled` result는 ordinary retirement와 audit에만 사용하며 별도 사용자 문장을 만들지 않는다. `duplicate_or_spent_stop_claim`은 새 사용자 request로 인정하지 않는다. 같은 open top-level dispatch에서는 proof-owned response-emission CAS winner만 local 문구를 publish하고, dispatch가 닫힌 뒤의 replay는 새 live proof를 만들 수 없으므로 별도 장기 tombstone 없이도 추가 publish가 0회다. 따라서 original-first/control-first 도착 순서와 무관하게 terminal 출력/발화는 최대 1회다.

위 stale 연결 문구는 control envelope 자체의 current `session_id/server_connection_generation` mismatch에만 사용한다. well-formed stale requested target identity는 §10.2에 따라 current context/none으로 resolve해 global stop을 계속하므로 이 거절 문구를 사용하지 않고 실제 completed/unknown 증거에 맞는 terminal을 사용한다.

비동기 terminal은 이미 종료된 Gradio generator turn에 새 Chat bubble을 append할 수 있다고 가정하지 않는다. 초기 구현의 sink 계약은 다음과 같다.

```text
immediate accepted/rejected response:
  local Chat source -> Chat UI yield once + output/TTS once
  microphone source -> output/TTS once

verified stop terminal response:
  routed external output/TTS once
  Chat UI asynchronous push -> NOT_IN_INITIAL_SCOPE
```

향후 Chat bubble push가 필요하면 Gradio turn 재사용이 아니라 별도 UI push adapter와 delivery test를 추가한다.

### 12.3 Busy, reconciliation, and disconnect

STOP은 emergency control이므로 ordinary `minecraft_command_busy`만으로 거절하지 않는다. Python ordinary command ownership을 선제 clear하지 않고 별도 lane과 admission barrier를 사용한다.

- live handshake/session/generation/capability가 있으면 active/reconciliation 상태에서도 one-shot stop control을 보낼 수 있다.
- Python pending/active context의 complete immutable retirement snapshot을 만들 수 있을 때만 `tracked_command`를 사용하고 Java에서 재검증한다.
- Python ordinary context가 없거나 complete immutable retirement identity를 만들 수 없으면 명시적 `current_global_automation` scope를 사용하며 target field를 보내지 않는다.
- Java에서 valid tracked target이 retired/replaced로 판명돼도 current context/none을 capture하고 global StopCommand를 실행한다. 이는 original retirement correlation만 약화시키며 stop 권한을 없애지 않는다.
- WebSocket send 결과가 불명확하거나 연결이 끊기면 자동으로 재전송하지 않는다.
- 확정적인 local rejection은 claim만 소비하고 barrier를 만들지 않는다. send commit 뒤 `REJECTED_BEFORE_WRITE`는 exact tracker CAS로 tracker/barrier를 함께 해제한다. matching no-mutation `rejected/deadline_exceeded` result도 stop tracker/barrier만 해제하고 frozen ordinary owner는 변경하지 않는다.
- send acceptance나 post-mutation terminal이 불명확하면 §11.4 quarantine을 유지하며 generic reconnect/reconciliation로 해제하지 않는다.
- preflight local disconnect처럼 tracker/barrier를 만들기 전에 확정 거절된 경우에는 live handshake가 복구된 뒤 사용자가 새 정지 발화를 해야만 새 control이 생긴다. 반대로 accepted/send-unknown/post-mutation unknown 또는 result-profile construction quarantine이 남아 있으면 reconnect와 새 발화로도 새 control을 만들지 않고 `stop_control_in_flight`로 거절하며, full dual-process reset만 기존 quarantine을 폐기한다.

다음 rollback 단위를 섞지 않는다.

## 18. Completion criteria

미래 구현은 다음 조건을 모두 만족해야 완료다.

1. Feature A/B/C는 실제 LAVI Chat 또는 VoiceInput-final adapter가 생성/stamping만 한 exact event를 factory-bound 별도 coordinator가 one-shot producer capability로 등록하고, top-level dispatch가 `DISPATCH_OWNED -> CONSUMED`한 뒤 허용 tuple과 Korean-eligibility까지 만족할 때만 새 동작을 소유한다. adapter에는 registry lifecycle 책임이 없다.
2. caller-created/copied/replayed/same-fields event와 terminal event의 재등록은 proof와 Feature A/B/C 전용 새 submit·routed-response publisher·`STOP_AI` control이 0회이고 pre-existing route/fallthrough는 동일하다. Chat은 `REGISTERED -> DISPATCH_OWNED`, Voice는 explicit queue acceptance에서만 `REGISTERED -> QUEUE_OWNED -> DISPATCH_OWNED`로 handoff한다. no-subscriber/enqueue failure, queue clear/drop/shutdown과 dispatch 포기에서는 exact current token owner만 `ABANDONED`로 닫고, queue acceptance 뒤의 unrelated listener/worker-start failure는 producer가 claim을 되돌리지 못한다.
3. 같은 한국어 문구라도 scope 밖 source/partial input이면 새 submit/publisher/control이 0회이고, Hangul 없는 입력의 기존 동작도 변경되지 않는다.
4. eligible Korean Chat과 마이크의 handled Minecraft command가 무응답으로 끝나지 않는다.
5. 각 response generation과 sink에서 응답은 exactly once이고 LLM 재호출/재귀/명령 재제출이 없다. STOP의 각 Python-local reason은 §12.2의 truthful 문구 또는 명시적 no-additional-publish 규칙에 정확히 매핑된다. duplicate/spent claim loser는 dispatch-scoped response CAS에서 지고 추가 Chat/output/TTS가 0회이며, state는 dispatch 종료 때 제거되어 4096건 초과 순차 처리에도 누적되지 않는다. 비동기 STOP terminal dedupe는 별도 무한 ledger가 아니라 최대 1개 Python tracker의 terminal-delivery CAS가 소유하고 tracker retire 뒤 late stop result는 재발화하지 않는다.
